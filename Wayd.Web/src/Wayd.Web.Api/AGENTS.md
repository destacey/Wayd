# AGENTS.md — Web API

The root [AGENTS.md](../../../AGENTS.md) applies here too. This file covers the two generation steps the API drives — the OpenAPI document and client, and the Wolverine handler tree — the hosted MCP endpoint built on the first, and how background jobs fail.

## Background Jobs

A `JobManager` job fails when its work did not happen and sets `[AutomaticRetry]` explicitly: [Background jobs](../../../docs/contributing/architecture.mdx#background-jobs).

## Hosted MCP Endpoint (`/mcp`)

`Mcp/` serves the API as agent tools; [mcp-server.mdx](../../../docs/contributing/mcp-server.mdx#the-hosted-endpoint) has the design.

- **A tool is an action marked `[McpTool(name, title)]`.** Its description is the `[EndpointSummary]` and `[EndpointDescription]`, its input schema the operation's parameters plus `requestBody`, so editing either changes what agents read. Never rename a tool.
- **Its output schema is the operation's success response**, so describe the response model truthfully: clients may
reject a result the schema does not accept. A non-object response is wrapped under `result` (`ToolOutput`).
- **Every controller with a tool carries `[McpTools(McpToolset.X, "wayd-x")]`**: its toolset (`McpToolFilter`) and the skill its tools point to. `McpToolCatalog` throws without it. Never rename a toolset.
- **Annotations default from the HTTP method**; set `ReadOnly`/`Destructive`/`Idempotent` on the attribute only to depart from it, and `Destructive = false` only for a write that purely adds a record.
- **Calls run through the API pipeline** (`ApiPipeline`), so a tool needs no authorization of its own — the endpoint's applies. An action whose body is not JSON cannot be a tool; `McpToolCatalog` throws on first use.
- **A partial update is a PATCH over the existing update request** via `JsonPatchControllerExtensions.Patch`, with a drift test; never a new command ([Partial updates](../../../docs/contributing/api.mdx#partial-updates)). Its tool swaps the full tool's verb for `Patch`.
- **Published tools stay**: `McpToolCatalogTests` holds the tool list to `Wayd.Web.Api.IntegrationTests/Mcp/published-tools.json`, the retired `@wayd/mcp` package's tools — every one stays, with its title, annotations and arguments. The same tests check that `docs/getting-started/mcp-server.mdx` and the skill evaluation's scenarios name only tools that exist.

## OpenAPI Client Generation

A Debug build writes the OpenAPI document with `Microsoft.AspNetCore.OpenApi` (`GenerateOpenApiDocument` target → `wwwroot/api/v1/specification.json`), then `GenerateApiClient` runs Orval to write `wayd.web.reactclient/src/services/api/`, warning instead without the client's `node_modules`. The transformers in `Wayd.Infrastructure/OpenApi/` decide the client's names, types and optional properties, so read the `src/services/api/` diff after changing one — see [api.mdx](../../../docs/contributing/api.mdx#openapi).

**CSV import columns are generated too, but not by the build.** Each import action carries `[CsvImport(key)]`, each file parameter `[CsvRows(typeof(Row))]` naming the class it passes to `ReadCsv`, and enum-parsed text columns `[CsvValues(typeof(Enum))]`; `CsvImportOperationTransformer` publishes them in the spec. After changing a row class, rebuild the API and run `npm run generate:import-templates` in the client — `import-templates.generated.test.ts` fails until you do. A new import endpoint also needs its entry in `SUBMITTERS` and `IMPORTED_RECORD_TAGS` (`store/features/admin/imports-api.ts`); both are keyed by the generated `ImportKey`, so the compiler asks for them.

**The document target boots the real API**, so a Debug build starts the application. `WAYD_SKIP_DB_INIT=true` (set by the MSBuild target) drives `HostIntrospection.SkipsDatabaseInitialization`, which skips every piece of startup work that touches the database — EF migrations and seeding, and the Hangfire server — so a Debug build does **not** require a running database. Gate any new database-touching startup work the same way: an ungated one fails the *build* (`Build FAILED`, real cause buried in the document tool's output; under Aspire just `The project could not be built.` and exit code 6) instead of erroring at runtime.

## Wolverine Handler Codegen (generated, not committed)

The Wolverine handler tree at `Wayd.Web.Api/Internal/Generated/WolverineHandlers/` is **git-ignored and generated by `codegen write`, never committed**. The codegen mode is chosen by the `Wolverine:CodegenMode` config key (see `WolverineConfiguration.ResolveTypeLoadMode`):

- **Local dev → `Auto`** (`appsettings.Development.json` sets `Wolverine:CodegenMode = Auto`). Wolverine compiles handlers at runtime via `WolverineFx.RuntimeCompilation`, so a plain `dotnet run`/build needs no pre-generated tree and no codegen step. **A local build never compiles the tree**: `Wayd.Web.Api.csproj` includes it only when `CI=true` or `WAYD_STATIC_HANDLERS=true`. Auto prefers a compiled handler type over compiling one, and writes what it compiles back into the folder, so compiling a local tree would freeze every handler at the moment it was written — a later dependency change silently keeps running the old code.
- **CI-tested builds and every published artifact → `Static`** (the default when the key is absent). Loads the pre-generated tree with no runtime Roslyn, for fast cold start. **Production is guarded**: a Production host resolving to anything but Static throws at boot. `WolverineFx.RuntimeCompilation` is referenced so Auto works in dev/tests but is never invoked on the Static path.

How the tree reaches tests and the image (`.github/workflows/docker.yml`, the API `Dockerfile`):

- CI's `api` integration shard generates the tree **once** (`codegen write`, in the `.github/actions/build-api` action), then runs `Wayd.Web.Api.IntegrationTests`, the one suite that boots it; it forces `CodegenMode=Static` under the same two switches (`HandlerCodegenMode`), so in CI it boots that exact tree — validating the shipped dispatch path — while a local run compiles fresh handlers. To run the Static path locally, generate the tree and set `WAYD_STATIC_HANDLERS=true` for both the build and the test run. The shards come from `.github/scripts/dotnet-test-projects.sh`.
- Off pull requests that shard also publishes the API with the tree compiled in (`api-image` artifact), and `build-and-push-image` copies it into the image with the Dockerfile's `prebuilt` target. **One generation per pushing run ⇒ the shipped tree is the tested tree.** On a PR, `build-api-image` makes its own; that image is never pushed.
- The Dockerfile's default target builds from source for `docker compose` and needs the tree in the build context (guarded). CI builds it only in `build-compose-images`, when a PR changes a file that job lists; keep that list in step with the `restore-inputs` stage.
- Codegen output is **DI-registration-order sensitive and not reproducible across environments** (even the OTLP exporter's presence reorders it), which is *why* it is generated once and shared rather than regenerated independently.
- The `codegen write` boot's environment (Development, `WAYD_SKIP_DB_INIT`, a placeholder connection string it never opens, no OTLP endpoint) is set and explained in `.github/actions/build-api/action.yml`.
- A broken codegen config is invisible to `dotnet build` and unit tests — only a real host boot and the `Wayd.Web.Api.IntegrationTests` dispatch suite catch it.
- Service location is disabled (`ServiceLocationPolicy.NotAllowed`): codegen constructor-inlines handler dependencies. A handler dependency whose registered implementation class is `internal` needs an `AlwaysUseServiceLocationFor<T>()` allow-list entry in `WolverineConfiguration` (or a public implementation) — otherwise `codegen write` fails with an `InvalidServiceLocationException` naming the type.
- **Two entries on that allow-list are there for correctness, not opaqueness, and removing either breaks behaviour rather than the build.** `AmbientUserId`: the middleware-written user id must be the same instance every consumer in the scope reads. **Every `IXxxDbContext` facade and `WaydDbContext` itself**: inline construction gives a handler that takes two of them two change trackers, and silently loses the work of one — see [Database](../../../Wayd.Infrastructure/AGENTS.md#database).
