# Frontend Development

The Wayd frontend is built with **Next.js 16** (App Router), **React 19**, **TypeScript**, and **Ant Design**.

## Project Structure

```
wayd.web.reactclient/
  src/
    app/              # Next.js App Router pages and layouts
    components/       # Shared components
      common/         # Generic reusable components
      contexts/       # React context providers (auth, theme, messaging)
      hoc/            # Higher-order components (feature flags)
    hooks/            # Custom React hooks
    services/         # API clients and services
      wayd-api.ts     # NSwag-generated TypeScript client
      clients.ts      # Client factory functions
    store/            # Redux Toolkit store and slices
    styles/           # Global styles and CSS modules
```

## API Calls

**Always use the NSwag-generated typed client:**

```typescript
import { getWorkItemsClient } from '@/src/services/clients'

const client = await getWorkItemsClient()
const workItems = await client.getList(workspaceId)
```

**Never use `authenticatedFetch()` directly** unless the generated client doesn't have the method yet.

## Styling

Use **Ant Design theme tokens**. Never hardcode colors.

Prefer CSS variables in CSS modules:
```css
/* good */
.header { color: var(--ant-color-primary); }

/* bad */
.header { color: #1677ff; }
```

Only use `theme.useToken()` when you need token values in JavaScript logic.

## State Management

Where a value lives is decided by **how long it should survive**, applied in this order:

1. **Would I share this?** → URL query param
2. **Should it outlive the browser?** → `localStorage`, owned by a Context or slice
3. **Should it survive leaving the page and coming back?** → Redux slice, keyed by record id
4. **Otherwise** → `useState`

Most state is (4). Every persisted value has exactly **one owner** — a Context or a slice — never a component calling `useLocalStorageState` directly.

See **[Record Pages](./record-pages.mdx#where-page-state-lives)** for the full rules, including how to model dialogs and what not to put in Redux.

## Responsive

**Every page must work at every width** — this is a requirement, checked before opening a PR, not an enhancement.

Use Ant Design's `useBreakpoint`. The app's conventions:

- `!screens.md` (&lt;768px) is the mobile cut — `AppSideNav` returns `null` and navigation moves to the header Drawer
- `!screens.sm` (&lt;576px) is the extra-small cut used by `PageTitle` for stacking
- `ResponsiveFlex` handles the common "stack on small screens" case

Three rules that apply to every page:

- **Horizontal scroll belongs to the element, never the page.** Wide grids, timelines and tables scroll inside their own container; the page body never scrolls sideways.
- **Hit targets ≥44px** on anything tappable.
- **Virtualized content needs a measurable height.** `WaydGrid` renders zero rows in an unconstrained `<Flex vertical>` parent — keep it a block-level child.

### Testing

Use the browser device toolbar (`Ctrl/Cmd+Shift+M`). In development a **breakpoint chip** in the bottom-right corner shows the active Ant Design breakpoint — mounted from the root layout behind a `NODE_ENV` check.

Test at **1440 / 1100 / 834 / 390**, and at the boundaries either side of any rule you rely on — bugs live at 767/768 and 991/992, not at 390.

See **[Record Pages](./record-pages.mdx#responsive)** for the full per-slot behaviour and checklist.

## Filter Bars

A filter bar is the row of small toggle buttons above a list — statuses, roles, personas. Two rules
hold across every one of them:

**Unselected buttons are dashed.** Selected ones keep a solid border. The dash is the primary
selection cue, and it is deliberately not a color: the PPM statuses roll up to four lifecycle
categories, and the not-started grey is close enough to an unselected button that colour alone
cannot separate them — measured in the browser, a selected grey chip differed from an unselected one
by a 10/255 background step. A dash also survives for a colourblind reader, who would otherwise have
only that step to go on.

**Colour means identity, never state.** Where a button has a status colour, it wears the same
background, border and text its tag uses in the Status column (`getLifecycleCategoryStatusSurface`),
so the bar and the grid speak the same vocabulary. Unselected buttons drop that colour entirely.
Where a filter has no colour of its own — roles, or the states on roadmaps and strategic themes —
the selected button keeps antd's primary rather than borrowing a meaning it does not carry.

```tsx
<Button
  size="small"
  color={isSelected && !surface ? 'primary' : 'default'}
  variant="outlined"
  style={
    isSelected
      ? surface
        ? {
            backgroundColor: surface.background,
            borderColor: surface.border,
            color: surface.text,
          }
        : undefined
      : { borderStyle: 'dashed' }
  }
>
```

Key the dash on **selection**, not on whether a colour was found — a filter with no colour would
otherwise render its selected button dashed, marking the active one as off.

`PpmFilterBar` (`src/app/ppm/_components/ppm-filter-bar.tsx`) is the shared implementation behind the
projects, programs, strategic initiatives, roadmaps and strategic themes bars; the My Projects
dashboard and story-map persona bars have their own markup and follow the same rules.

## Data Grids

All data grids use the **`WaydGrid`** house component (built on TanStack Table) — never Ant Design's `Table` or raw TanStack Table. It provides a consistent toolbar, Excel-style column filters, sorting, column sizing/visibility/pinning/reordering, row virtualization, CSV export, opt-in column-layout persistence, and (opt-in) tree mode, drag-and-drop, and inline editing.

See **[WaydGrid](./wayd-grid.mdx)** for the full usage guide — props, column `meta`, how to enable/disable each feature, and persistence.

## PWA (Progressive Web App)

The client app is installable as a PWA, providing a native app-like experience with app shell caching and network-first API strategy.

**Key files:**

| File | Purpose |
|------|---------|
| `src/app/manifest.ts` | Web app manifest (name, icons, screenshots, theme color) |
| `src/app/sw.ts` | Service worker source (precaching + runtime caching) |
| `src/app/serwist/[path]/route.ts` | Turbopack route handler that builds and serves the SW |
| `src/config/theme/theme-constants.ts` | Shared brand color used by manifest and light theme |
| `public/icons/` | PWA icons (192x192, 512x512) |
| `public/screenshots/` | Install dialog screenshots (desktop and mobile) |

**Tooling:** [Serwist](https://serwist.pages.dev) (`@serwist/turbopack`) — handles service worker compilation and precache manifest injection via a Next.js route handler.

**Development:** The service worker is only active in production builds. To test PWA features locally, run `npm run build && npm start`.

**Caching strategy:** `defaultCache` from Serwist provides network-first for navigations and API calls, and cache-first for static assets (JS, CSS, images, fonts).

## Theming

Theming has two orthogonal axes:

- **Theme** — a visual identity (shape language, typography, surface treatments): **Wayd** (the default), **Cartoon**, **Shadcn**, **Glass**, **Geek**, and **Illustration**.
- **Mode** — a color-scheme variant of a theme: `light`, `dark`, or `slate` (the Wayd theme's alternate dark). Each theme declares which modes it supports; single-mode themes (e.g. Geek is dark-only) simply declare one.

On top of that, users can customize density and (for eligible themes) primary color. All theming is built on Ant Design's `ThemeConfig` and `ConfigProvider`; a mode maps to an algorithm + token seed, exactly like Ant Design's `darkAlgorithm`/`compactAlgorithm` model.

The active selection is exposed on `<html>` as two attributes: `data-theme` (identity) and `data-mode` (color scheme). Global CSS keys mode-dependent rules (e.g. scrollbars) off `data-mode` and identity-dependent rules (e.g. background textures) off `data-theme`.

### Adding a new theme

1. Create `src/config/theme/my-theme.tsx` exporting an `AppThemeConfig` hook (one per supported mode)
2. Add `'my-theme'` to the `ThemeId` union in `types.d.ts`
3. Add its entry to `THEME_METADATA` (label, `defaultMode`, supported `modes`) and wire the preset hook(s) into `useThemeRegistry` in `theme-registry.tsx`
4. If the theme needs identity-specific CSS (backgrounds, scrollbars), key it off `[data-theme='my-theme']` in `styles/globals.css`; mode-generic rules already apply via `[data-mode='...']`
5. Set `behavior.allowsPrimaryOverride` explicitly in the theme config

The theme select and mode control in `theme-manager-drawer.tsx` are driven by `THEME_METADATA`, so no UI change is needed.

### Adding a mode to an existing theme

1. Create the mode's `AppThemeConfig` hook (e.g. a dark variant of Glass)
2. Add the mode to the theme's `modes` list in `THEME_METADATA` and its config to `useThemeRegistry`

The mode control appears automatically for any theme with more than one mode.

### User theme overrides

Per-user overrides (`colorPrimary`, `useCompactAlgorithm`) are stored as JSON in the `Preferences` column on `Identity.Users` via `UserThemeConfig`. They're loaded from `GET /api/user-management/profiles/theme` on mount and saved debounced (500ms) via `PUT` on change.

`mergeThemeConfig` in `theme-context.tsx` layers these overrides on top of the base theme.

- `useCompactAlgorithm` is always eligible.
- `colorPrimary` is only applied when the active theme sets `behavior.allowsPrimaryOverride = true`.

When switching themes from the Theme Manager, any custom primary override is cleared so the newly selected theme starts from its own default primary color. Switching modes within a theme keeps user overrides — it's an appearance flip, not an identity change.

### Theme context

Consume the theme context via `useTheme()`:

```typescript
const {
  currentTheme,      // ThemeId, e.g. 'wayd'
  currentMode,       // ThemeMode: 'light' | 'dark' | 'slate'
  availableModes,    // modes supported by the current theme
  setCurrentTheme,   // keeps the current mode when the new theme supports it
  setCurrentMode,    // ignored if the current theme doesn't support the mode
  token,
  userThemeConfig,
  setUserThemeConfig,
} = useTheme()
```

The selection persists in localStorage under the `appTheme` key as `{ theme, mode }`. Legacy flat values (a bare theme/mode name string from before the theme × mode split) are normalized transparently on read — `light`/`dark`/`slate` map to the Wayd theme in that mode; other names map to that theme in its default mode.

## Links

Two link styles, chosen by link *density*:

- **Sparse links** — a link surrounded by static text (prose, metadata rows, "View all"): use the standard blue link (`Typography.Link` / `<Link>`). Color is the affordance.
- **Dense links** — entity titles in lists, cards, and grids where nearly every item navigates: use `EntityLink` (`src/components/common/entity-link.tsx`). It renders in the default text color with semibold weight; hover and keyboard focus reveal the affordance (primary color + underline). The surrounding collection already implies interactivity, so painting every title blue is noise.

Rule of thumb: *is this link surrounded by other links? `EntityLink`. Surrounded by static text? blue.*

In grids, keep the entity **key column** as a standard blue link (the row's anchor) and use quiet styling for name/title columns. Reserve the chain icon for "copy link" affordances and the external-link icon for navigation that leaves Wayd — icons are not link indicators.

## Rendering user markdown

User-supplied markdown (project/portfolio descriptions, business cases, risk descriptions, health-check notes) renders through `MarkdownRenderer` (`src/components/common/markdown/`). It enables `rehypeRaw`, so raw HTML embedded in that text is parsed — which means it **must** be sanitized before it reaches the DOM.

The plugin order matters and is load-bearing:

```tsx
rehypePlugins={[
  rehypeRaw,                      // parses raw HTML
  [rehypeSanitize, sanitizeSchema] // must come AFTER rehypeRaw
]}
```

Sanitizing before `rehypeRaw` leaves the raw HTML unparsed at that point, so it passes through untouched — the ordering is the control, not the presence of the plugin.

`sanitizeSchema` (`sanitize-schema.ts`) is the default `rehype-sanitize` schema plus `<u>`, which the renderer maps to antd's underline `Text`. The default schema keeps GFM tables, task lists and `language-*` code fences intact while dropping `<iframe>`, `<form>`, `<base>`, `<meta>`, `<style>`, event-handler attributes and the `style` attribute.

:::warning Check additions against the overlay case
Anything added to `tagNames` or `attributes` must be checked against clickjacking. An attacker who can set `style` on any element can cover the page with a full-viewport overlay — that is same-origin, so no CSP prevents it. `sanitize-schema.test.ts` covers this case explicitly; keep it passing.
:::

The docs viewer is a **separate** pipeline (`next-mdx-remote` / `MDXRemote`) rendering repo-authored content, and does not go through `MarkdownRenderer`.
