# KPIs

KPIs are one model in `Wayd.Common` that any module puts on its own records, the way [discussions](./architecture.mdx#discussions) are. A record carrying KPIs is a **subject**, held by a registered **subject type** and an id. The core never knows what a team is: each module registers its subject types and answers, for each, who may read and change a record's KPIs. Teams and teams of teams are one subject type; projects, programs and portfolios are three more, registered by PPM.

The user-facing rules are in [Scorecards and KPIs](../user-guide/organizations/scorecards.mdx).

## Where it lives

| Piece | Path |

| Commands, queries, the import | `Wayd.Common.Application/Kpis/` |
| Tables (`Kpis` schema) | `Wayd.Infrastructure/Persistence/Configuration/KpisConfiguration.cs` |

| Endpoints | `KpisController` (`/api/kpis/{subjectType}/{subjectId}`), `KpiCategoriesController`, `KpiImportsController` |

Strategic initiative KPIs moved onto this model as the `ppm.strategic-initiative` subject type. `Move-Strategic-Initiative-Kpis-To-Shared-Model` copied each with its checkpoints and measurements, keeping their ids, and wrote a `KpiBaselinedEvent` for each; `Drop-Strategic-Initiative-Kpi-Tables` ran the copy again for anything written since, then dropped the `Ppm.StrategicInitiativeKpi*` tables. The `StrategicInitiativeKpi*` events are `[Obsolete]` and stay only so the entries already in an initiative's Activity keep reading.

## The goal and its readings

A KPI stores what was entered — the baseline, the target as a rule (`Absolute` or `RelativeChange`), the optional at-risk threshold (`Absolute` or `ProgressToTarget`) — never the values they resolve to. `KpiGoal` resolves them and validates them together, since each constrains the others: a relative target needs a baseline, and the baseline must be short of the target in the KPI's direction. Correcting the baseline therefore moves a relative target with it.

A measurement stores the raw value only. `KpiReading.Of` works out the change from baseline, the progress to target, the health and the trend from the latest two values when read. It is a pure function of values, so the scorecard query reads each KPI's newest values in SQL and builds the reading without loading the aggregate.

The measurements belong to the `Kpi` aggregate so that the rule that no two periods on a KPI overlap is checked in one place. Every command that changes a measurement loads them with `.Include(k => k.Measurements)`; the in-memory fakes cannot tell when it is missing. Two concurrent saves are each checked against the measurements their own request loaded, so every measurement change also writes the KPI's row (`KpiCommandScope.SaveMeasurements` → `IKpisDbContext.TouchKpi`): its row version makes the second save a 409 rather than letting two overlapping periods both land.

## Authorization

Every KPI command and query goes through `KpiSubjectAccessResolver`, which asks the record's subject type and then applies two rules once for every subject type: **Administer KPIs** (`Permissions.Kpis.Administer`) manages any record's KPIs, and a read-only token manages none. The endpoints carry `[Authorize]` only, so the handler's check is the whole gate. A record the caller cannot read is 404, never 403.

The team subject type, `TeamKpiSubjectType`, reads a team's KPIs with `Permissions.Teams.View`, and lets them be changed by members of the team or of any team of teams above it as the hierarchy stands today — not only the direct parent, unlike sprints and allocations.

The PPM subject types (`ProjectKpiSubjectType`, `ProgramKpiSubjectType`, `PortfolioKpiSubjectType`) read with the record's `View` permission and let a record be changed by the rule every other change to it follows: its `Update` permission and delivery leadership, through the aggregate's own `CanManage*` predicate, with the PPM administrator standing in for the role. Each loads the ancestors' roles with `.Include` — without them the predicate silently finds no inherited leader — which only a real provider can check (`PpmKpiSubjectTypeTests` in the PPM integration tests). A closed record's KPIs stay changeable. `StrategicInitiativeKpiSubjectType` needs no leadership: the initiative's `Update` permission alone changes its KPIs, as it does every other part of an initiative.

A module deleting a record calls `IKpiWriter.RemoveAll` beside `ILinkWriter.RemoveAll`: a KPI has no foreign key to its subject, so it would otherwise outlive it.

The import is gated on Administer KPIs rather than on each record's rule: its passes may run after the request has ended, when there is no caller to ask about membership.

## Adding a subject type

To put KPIs on another kind of record:

1. **Declare the descriptor** in the module's domain project, as a static field beside a `Register()` method, like `OrganizationKpiSubjects`. Its key (`ppm.project`) is persisted on every KPI and must never change; its activity aggregate type must be the one the record's own events are filed under, so KPI changes show in the record's Activity.
2. **Implement `IKpiSubjectType`** in the module's Application project, public so Wolverine's generated handlers can construct it:
   - `Resolve` returns null when the record does not exist or the caller cannot read it, and otherwise its name, its code, and whether the caller may manage its KPIs by the record's own rule. Do not apply the KPI administrator's waiver or the read-only limit here; the resolver applies both.
   - `Describe` answers which of a set of ids exist, with the link to each, without asking anything of the caller. The import uses it to check rows and to link its results.
3. **Register both** in `Wayd.Infrastructure/Kpis/ConfigureServices.cs`: the descriptor's `Register()` call and the implementation.
4. **Add the subject type to the client**: its key in `KpiSubjectTypes` in `kpis-api.ts`, and a `KpiScorecard` section on the record's page behind the `kpis` flag.
5. **Cover it in tests**: the subject type's rule against an in-memory context, and against SQL Server when it walks a hierarchy or a navigation, as `TeamKpiSubjectTypeTests` does.
6. **Update the docs**: the user guide page for the record, the permissions page, and the subject type tables in the `wayd-kpis` skill and in the KPI import's columns.

No migration is needed: every subject type shares the same tables.
