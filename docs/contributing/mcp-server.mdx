# MCP Server

Wayd exposes its API as agent tools in two ways: the hosted endpoint at `/mcp`, served by `Wayd.Web.Api`, and the `@wayd/mcp` npm package, which is being retired once the hosted endpoint has replaced it.

## The hosted endpoint

`/mcp` serves MCP over Streamable HTTP, statelessly, with the official C# SDK (`ModelContextProtocol.AspNetCore`). It is behind the `mcp-server` feature flag and requires an authenticated caller: a personal access token in `x-api-key`, or the Wayd JWT. The code lives in `Wayd.Web.Api/Mcp/`.

**Discovery follows the MCP authorization spec.** An unauthenticated call is refused with a 401 whose `WWW-Authenticate: Bearer resource_metadata="…"` header points at `/.well-known/oauth-protected-resource/mcp`, the endpoint's protected resource metadata (RFC 9728), which names the API's public URL as the authorization server; a refused bearer token adds `error="invalid_token"`. `McpAuthentication` owns both: the endpoint's policy authenticates through the `Mcp` policy scheme, which forwards to the scheme the API's default policy would pick for the request and challenges with the SDK's MCP scheme, so a refusal carries exactly one challenge. The metadata path is fixed, so `/mcp/` and `/MCP` are pointed at the same document and no other path under the prefix is answered. While the flag is off, `McpFeatureGate` answers 404 for both paths ahead of authentication, so an unauthenticated caller is not challenged either. The challenge's and the metadata's URLs come from the API's [public URL](./configuration.mdx#public-url), not from the request, so they are right behind a TLS-terminating proxy. Wayd's subclass of the SDK's handler writes the whole challenge, so it can use the public URL, and replaces whatever `WWW-Authenticate` value was set before; that is safe only while the MCP scheme is the one scheme that challenges on `/mcp`. The public URL is an origin with no path, because the well-known documents OAuth clients look up sit at the host's root.

**A tool is a controller action marked `[McpTool]`.** The API is the only definition of each tool:

- **Name and title** come from the attribute: `[McpTool("Projects_GetProject", "Get project")]`. A tool name is a contract with the skills and prompts that already call it, so never rename one.
- **Description** is the action's `[EndpointSummary]` followed by its `[EndpointDescription]`. Write it for an agent choosing between tools; it is also the endpoint's published documentation.
- **Input schema** comes from the action's operation in the runtime OpenAPI document: one argument per path, query or header parameter, plus `requestBody` for a JSON body (a JSON Patch body is sent as `application/json-patch+json`, the only type a patch endpoint accepts). Parameter and property descriptions are the `<param>` and `///` documentation the OpenAPI document already publishes, and closed sets arrive as enum codes.
- **Output schema** comes from the operation's first success response with a JSON body, converted the same way but without request validation rules such as `minLength` and `pattern`, which the API does not hold its responses to, and a call answers with that body as `structuredContent` beside the same JSON as text. The schema is always an object, which protocol versions before `2026-07-28` require: a response that is anything else, an array or a created id, sits under `result`. A tool whose endpoint answers 204 has no output schema, and a tool with one that gets no body it describes, such as a 204 for a missing record, answers with an error rather than bare text. In both schemas, a type that inherits (`allOf` a base type and its own part) is combined into one, and a type with subtypes (`[JsonDerivedType]`) becomes `anyOf` its subtypes, each with its `$type`. Clients may reject a result its schema does not accept, so a response model the OpenAPI document describes wrongly breaks its tool; `McpEndpointTests` calls every read-only tool that needs no arguments and validates each answer.
- **Result size** is capped at `ApiToolResult.MaxResultLength` characters (about 20,000 tokens), because most list endpoints return every matching record. A longer answer has items dropped from the end of its lists until it fits: the body itself when it is an array, otherwise the arrays directly on it, largest first, so a summary beside a list survives whole. A second text block then says what was kept and how to ask for the rest; it stays out of `structuredContent`, which must still match the output schema. Nested lists are not cut, so a tree loses whole top-level nodes. A result that is a list keeps at least one item even when that item alone is over the limit, and a single record with no list is returned whole.
- **`offset`** reaches the rest of a cut list. The catalogue adds it to every read tool whose result is an array, unless the endpoint already pages or limits its own answer (`page`, `pageNumber`, `pageSize`, `take`, `top`, `limit`): an offset there would slice only the rows the endpoint chose to return. A whole number sent as `5.0` or as text is accepted, as other arguments are. The tool reads it itself and never sends it: the endpoint still returns the whole list, the tool skips `offset` items and cuts what remains, always keeping one item so each call moves forward, and the note gives the offset that continues (`Call again with offset=74`). Slicing is only consistent while the endpoint's order is, so **a list endpoint orders its query by a unique key**; one that returns rows in whatever order the database chooses can repeat or skip items between calls. A result object holding a list (a record and its children, a rollup and its items) gets no `offset`, and its list is only cut.
- **Toolset** comes from `[McpTools(McpToolset.Ppm)]` on the controller, and every controller with a tool needs one; the catalogue throws on first use otherwise. Toolset names are part of client configurations, so never rename one.
- **Annotations** default from the HTTP method, as the npm package's did: only GET is read-only, every write starts destructive, PUT and DELETE are idempotent, and every tool is `openWorldHint: false`. Set `ReadOnly`, `Destructive` or `Idempotent` on the attribute only to depart from that. A write is advertised as safe (`Destructive = false`) only when it purely adds a record.

**A call runs through the endpoint itself.** `ApiPipeline` sends the arguments as an HTTP request through the API's own middleware pipeline, in process, carrying the caller's credentials. Authentication, `[MustHavePermission]`, feature gates, model validation, the controller's own checks and the domain's delivery-leadership rules all apply exactly as they do to the same HTTP request, and a refusal comes back as a tool error naming the status and the reason.

The two import tools, `Imports_GetFileFormat` and `Imports_Preflight`, front every import endpoint at once, so they are written by hand in `ImportTools`, in the `imports` toolset.

**Prompts are generated from `skills/`.** The build embeds every `.md` under the repository's `skills/` in `Wayd.Web.Api`, and `SkillPrompts` serves one prompt per skill folder: named after the folder, titled by its `SKILL.md` heading, described by that file's frontmatter `description`, with no arguments. Its messages are `SKILL.md` without the frontmatter, then every other `.md` in the folder at any depth, in path order. Every connection gets every prompt, whatever toolsets it chose. To change a prompt, edit the skill; `SkillPromptsTests` holds the prompts to the files. Clients show prompts as commands a user picks, so a model does not reach for one unprompted: a workflow an agent must find on its own also carries a compact recipe in the description of the tool that ends it (`Projects_CreateProjectHealthCheck`, `PlanningIntervals_CreateObjectiveHealthCheck`), and the server instructions name those workflows.

**A connection chooses its tools.** `McpToolFilter` reads the toolsets (`toolsets` query parameter, else `X-MCP-Toolsets`) and read-only mode (`readonly`, else `X-MCP-Readonly`) from each request, refusing an unknown name with 400. The server is stateless, so the filter is applied to every request, `tools/call` included: a tool outside the selection cannot be called, and read-only mode, which keeps only tools annotated `readOnlyHint`, is enforced rather than advisory. A write tool wrongly annotated read-only would therefore leak into read-only connections, which is one more reason to leave annotations to the HTTP method.

While the npm package is still published, the hosted endpoint must offer every one of its tools. `Wayd.Web.Api.IntegrationTests/Mcp/npm-tool-parity.json` records each npm tool's name, title, annotations and arguments, plus the server instructions. The package's `tests/hosted-parity.test.ts` keeps it current (`UPDATE_PARITY_SNAPSHOT=1` rewrites it), and `McpToolCatalogTests` holds the API to it. A tool added to the npm package must be added to the API; the hosted endpoint may offer more, which is where composite tools live.

## The npm package

The `@wayd/mcp` package in `Wayd.Web/src/Wayd.Mcp` exposes the Wayd API as agent tools. It is published to npm separately from the application, so a deployed API and the MCP clients that call it can drift apart. For connecting a client to it, see [MCP Server](../getting-started/mcp-server.mdx).

### Every shipped change needs a changeset

The package is released with [changesets](https://github.com/changesets/changesets). A change merged to `main` without a changeset is **never released**: the release PR only picks up pending changesets. Nothing else fails, so a renamed or newly added tool can sit unreleased while the API it calls moves on. Clients on the published version then send fields the API no longer reads, or miss fields it now needs.

A change needs a changeset when it touches what the package ships:

- `src/` — tool definitions, the executor, the server
- `scripts/` — the generators that produce `src/generated/` at build time
- `README.md` and `package.json`
- the API's OpenAPI document (`Wayd.Web.Api/wwwroot/api/v1/specification.json`), **when it changes an import endpoint**. The import file formats are generated from it, so changing an import row class changes the package even when no MCP file changes.

Add one from `Wayd.Web/src/Wayd.Mcp`:

```bash
npx changeset          # choose patch / minor / major and describe the change
npx changeset --empty  # the change ships nothing worth releasing, on purpose
```

The package is pre-1.0, so a breaking change to a tool's inputs (a renamed or removed field) is a `minor` bump, and fixes are `patch`. Write the summary for the people calling the tools: name the tools and fields that changed, and what a caller sends now.

### How it is enforced

`.github/scripts/mcp-changeset-check.sh` fails when a branch changes any of the above without adding a changeset. A spec change counts only when regenerating the import formats from it changes them, so most API changes are unaffected.

- **CI** runs it as the `changeset` job of the MCP workflow on every pull request that touches the package or the spec. The release PR (`changeset-release/main`) is exempt, since it consumes the changesets.
- **The `pre-push` hook** runs it before every push, so you see it before the pull request does. It is enabled with the other hooks: `git config core.hooksPath .githooks`, once per clone. It skips itself, with a note, until `npm ci` has run in `Wayd.Web/src/Wayd.Mcp`. Bypass it with `git push --no-verify`.

Run it by hand against any base:

```bash
bash .github/scripts/mcp-changeset-check.sh origin/main
```

### Release flow

1. A pull request merges to `main` with its changeset.
2. The MCP workflow opens or updates the release PR, which bumps the version and writes `CHANGELOG.md`.
3. Merging the release PR publishes the package to npm and tags it `wayd-mcp-v<version>`.

## Skill layout

Each skill in `skills/` is a folder whose `SKILL.md` is the overview an agent loads when the skill triggers: the frontmatter `name` and `description`, the rules that apply to every call in its area, and a Reference table naming each file in its `reference/` folder and when to read it. Detail that only one workflow or area needs lives in `reference/*.md`, one level deep and linked from `SKILL.md` by relative path, so an agent reads it only when the task calls for it. Keep `SKILL.md` well under 500 lines.

## Skill evaluation

The skills in `skills/` are tested by scenarios in `Wayd.Web/src/Wayd.Mcp/evals/`: a user request, canned API responses, and the tool calls a correct run makes. Each runs through Claude Code against a stub of the MCP server, with and without the skills, on each model, and is graded on its tool calls. Run it before and after changing a skill, and add a scenario when a skill gains guidance worth testing. `npm test` checks that every scenario is well-formed; the evaluation itself is run by hand, because it uses a Claude Code plan. See the [evaluation README](https://github.com/destacey/Wayd/blob/main/Wayd.Web/src/Wayd.Mcp/evals/README.md).
