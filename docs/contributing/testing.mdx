# Testing

## Test Projects

Test projects mirror the source structure:
- `Wayd.\{ServiceName\}.Domain.Tests` - Domain logic tests
- `Wayd.\{ServiceName\}.Application.Tests` - Handler and validator tests
- `Wayd.\{ServiceName\}.IntegrationTests` - Run against a real SQL Server via Testcontainers
- `Wayd.ArchitectureTests` - Enforce Clean Architecture dependency rules

### Unit vs integration

A project is an **integration** project if it references `Testcontainers.MsSql`, and a **unit** project
otherwise. That one dependency is the source of truth for everything else: CI splits its two test jobs
on it, and each test assembly is stamped with a matching `Category` trait automatically. Nothing needs
tagging by hand, and the trait cannot drift from what a project actually requires.

Integration tests need Docker running. Unit tests never do — including
`Wayd.Integrations.AzureDevOps.IntegrationTests`, which despite its name needs a live Azure DevOps org
rather than a container, and skips itself when one is not configured.

### Sharing a container

Every integration project shares **one** SQL Server container and one migrated schema across all of its
test classes, via a collection fixture:

```csharp
[CollectionDefinition(Name)]
public sealed class SqlServerTestCollection : ICollectionFixture<SqlServerDbContextFixture>
{
    public const string Name = "SqlServer integration tests";
}

[Collection(SqlServerTestCollection.Name)]
public sealed class MyIntegrationTests(SqlServerDbContextFixture fixture) { }
```

Use `[Collection(...)]`, **never `IClassFixture<T>`**. xUnit constructs a class fixture once per test
class, so `IClassFixture` means a container start and schema migration for every class — which is what
made one suite take six containers to run 44 tests.

The consequence is that tests **share a database**. Scope assertions to data the test itself created
(a fresh `Guid`, a unique key) rather than assuming an empty schema or querying for "the only row".

## Test Naming

Test projects: `\{ProjectName\}.Tests`

Test classes and methods should clearly describe the scenario being tested.

## Test Structure

These conventions keep the suite consistent and easy to scan. New tests should follow them.

### One class per system-under-test, named after the file

Each test class targets a single system-under-test (SUT), and the class name matches its file name. Do **not** merge tests for several SUTs (e.g. multiple command handlers) into one class — give each handler its own `\{Handler\}Tests.cs` containing a class of the same name.

### Arrange / Act / Assert comments

Every test method marks the three phases with `// Arrange`, `// Act`, and `// Assert` comments so the flow reads at a glance. When the setup needs context, append a note to the marker:

```csharp
[Fact]
public async Task Handle_ShouldFail_WhenModelIsActive()
{
    // Arrange — an active model cannot be deleted; the handler's guard should reject it
    // and leave the row in place.
    var model = _faker.AsActiveWsjf();
    _dbContext.ScoringModels.Add(model);
    var command = new DeleteScoringModelCommand(model.Id);

    // Act
    var result = await CreateHandler().Handle(command, TestContext.Current.CancellationToken);

    // Assert
    result.IsFailure.Should().BeTrue();
    _dbContext.SaveChangesCallCount.Should().Be(0);
}
```

### Cancellation tokens

Pass `TestContext.Current.CancellationToken` to **every** method that accepts a `CancellationToken` — both the handler's `Handle(...)` call and any EF assertion queries (`SingleAsync(...)`, `AnyAsync(...)`, etc.). This is the dominant convention across the suite and clears the `xUnit1051` analyzer warning. Avoid `CancellationToken.None`.

## Fake Data

Domain fakers generate realistic test data with Bogus. They live in **each model's own test project**, under a `Data/` folder — not in `Wayd.Tests.Shared`. Only the `PrivateConstructorFaker<T>` base class lives in `Wayd.Tests.Shared`.

```csharp
var faker = new ScoringModelFaker();
var model = faker.Generate();
```

### Faker conventions

- **Per-property `With\{Property\}` builder extensions**, not a single `WithData(...)` with optional parameters. Each extension sets one `RuleFor` and returns the faker for chaining.
- **`With\{Property\}` means "set exactly this value."** Do not skip null values inside the extension. If a nullable property needs to be cleared, `WithDescription(null)` or `WithParentId(null)` should set the generated model's property to null.
- **`As...` state helpers** are for coherent domain states and may update several aligned properties together — e.g. `AsActive()` can set status, date range, and timestamps consistently. If an `As...` helper accepts optional parameters, it should call the relevant `With\{Property\}` method only when the optional value is supplied.
- **Composition helpers** that build child collections through the aggregate's own methods (so invariants and ordering hold) are encouraged — e.g. `AsProposedWith(scales, criteria, outputs)`.
- **Encapsulate shared fixtures as faker extensions**, not a separate `\{Thing\}TestData` holder class. When several test classes need the same realistic entity, add a convenience extension that builds the canonical fixture (e.g. `AsProposedWsjf()` / `AsActiveWsjf()` on `ScoringModelFaker`) and call it from each test. Keep small one-off fixtures inline.

### Fake DbContext

Fake `DbContext` implementations are available for each application area (e.g. `FakeWaydDbContext`), backing each `DbSet` with an in-memory list so handlers can be tested without a database. They track `SaveChangesCallCount`, which assertions use to verify a handler saved (or didn't) as expected. Combine with `NullLogger<T>.Instance` for the handler's logger.

```csharp
private readonly FakeWaydDbContext _dbContext = new();
private readonly ScoringModelFaker _faker = new();

private DeleteScoringModelCommandHandler CreateHandler() =>
    new(_dbContext, NullLogger<DeleteScoringModelCommandHandler>.Instance);
```

## Running Tests

```bash
# All tests (both halves; the integration suites need Docker running)
dotnet test Wayd.slnx

# Only the tests that need no Docker — what CI's unit job runs
./.github/scripts/dotnet-test-projects.sh unit

# Only the Testcontainers suites — what CI's integration job runs
./.github/scripts/dotnet-test-projects.sh integration

# Specific project
dotnet test "Wayd.Services/Wayd.Work/tests/Wayd.Work.Application.Tests/Wayd.Work.Application.Tests.csproj"

# By class name
dotnet test --filter "FullyQualifiedName~ProjectServiceTests"

# By category, within one project
dotnet test "<project>" --filter "Category=Unit"

# Architecture tests
dotnet test Wayd.ArchitectureTests/Wayd.ArchitectureTests.csproj
```

`--filter` matches per assembly and exits non-zero when an assembly contains no matching test, so a
filtered run across the whole solution fails on every project that happens not to match. Filter one
project at a time, or use the split script above.

### Test traits

Three independent axes are available for selecting tests:

| Trait | Values | Meaning |
|---|---|---|
| `Category` | `Unit`, `Integration` | How it runs and what it needs. Applied automatically per assembly — do not set by hand. |
| `Suite` | `Smoke` | A curated fast pass. Untagged tests are the default regression body. |
| `Area` | `PPM`, `Security`, … | What it covers, cutting across projects. |

Values live as constants in `Wayd.Tests.Shared` (`TestCategories`, `TestSuites`, `TestAreas`). Use
them rather than string literals: a filter with a typo matches nothing and still exits zero for that
assembly, so a mistyped trait silently runs fewer tests instead of failing.

## Frontend Tests

```bash
cd Wayd.Web/src/wayd.web.reactclient
npm test               # watch-friendly local run
npm run test:ci        # what CI runs on a PR
npm run test:coverage  # what CI runs on a merge to main
```

Uses Jest with React Testing Library.

Coverage instrumentation costs roughly four times the test run itself, so PRs run without it and only
the main-branch build collects it. Both the .NET and client coverage numbers are published to that
run's summary page.
