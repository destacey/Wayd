# Testing

## Test Projects

Test projects mirror the source structure:
- `Wayd.\{ServiceName\}.Domain.Tests` - Domain logic tests
- `Wayd.\{ServiceName\}.Application.Tests` - Handler and validator tests
- `Wayd.\{ServiceName\}.IntegrationTests` - Run against a real SQL Server via Testcontainers
- `Wayd.Web.Api.Tests` and `Wayd.Web.Api.IntegrationTests` - Controllers, request models, OpenAPI and MCP; the integration suite boots the real API
- `Wayd.Infrastructure.Tests` and `Wayd.Infrastructure.IntegrationTests` - Persistence, messaging, auth, identity and connector modules
- `Wayd.Integrations.\{SystemName\}.Tests` - External system clients
- `Wayd.Tools.DataGeneration.Cli.Tests` - The data generation tool, which seeds through the import endpoints
- `Wayd.ArchitectureTests` - Enforce Clean Architecture dependency rules (see [Architecture tests](./architecture.mdx#architecture-tests))

Shared helpers live under `Wayd.Common/tests/`: `Wayd.Tests.Shared` (traits, `TestingDateTimeProvider`, the
cross-cutting fakers, `MockDbSetFactory`), `Wayd.TestData.Core` (`PrivateConstructorFaker<T>`) and
`Wayd.Tests.Containers` (the SQL Server container).

### Unit vs integration

Every test assembly is stamped with two traits automatically, so nothing needs tagging by hand:

- `Category` says what kind of test it is. A `*.IntegrationTests` project is `Integration`; every other
  project is `Unit`.
- `Requires=Docker` marks a project that references any `Testcontainers*` package. CI splits its two test
  runs on this same dependency, so the trait cannot drift from the job a test runs in.

The two usually agree, with one exception. `Wayd.Integrations.AzureDevOps.IntegrationTests` is `Integration`
but has no `Requires` trait. It needs a live Azure DevOps org rather than a container, so it runs in CI's
unit half and skips itself when no org is configured.

The Testcontainers match is on the **prefix**, not on `Testcontainers.MsSql` specifically: a suite
reaching for a different module (`Testcontainers.PostgreSql`, `.Redis`, `.RabbitMq`) still needs Docker.
`Directory.Build.targets` and `.github/scripts/dotnet-test-projects.sh` must stay in step on this.

CI runs the unit half and the integration half as parallel jobs, and splits the integration half into
shards, one job each. `Wayd.Infrastructure.IntegrationTests` and `Wayd.Web.Api.IntegrationTests` each have a
shard of their own (`infrastructure`, `api`) because they set the pace of the run; the `other` shard takes
every remaining integration project, so a new suite lands there without any change. The shards are defined in
`dotnet-test-projects.sh`, and the integration matrix in `.github/workflows/docker.yml` must list them
exactly, in the same order, or every shard fails.

Each integration run (one per shard in CI) starts **one** SQL Server container for every suite in it and hands its connection string
to the test processes as `WAYD_TEST_SQLSERVER`. The engine upgrades its system databases on every first
boot, which takes about a minute, so sharing it pays that once per run instead of once per suite. The
script removes the container when the run ends, pass or fail, and prints its log when the run fails. It
runs at most four projects at a time; set `INTEGRATION_TEST_PARALLELISM` to change the limit, and
`SQLSERVER_MEMORY_LIMIT_MB` to change the engine's memory (6144 by default).

Leave `WAYD_TEST_SQLSERVER` unset and a project run on its own, from an IDE or `dotnet test`, starts one
container, which the collections running together share, so no setup is needed.

### A long-lived test engine

Every run without `WAYD_TEST_SQLSERVER` waits about a minute for an engine to boot, which is most of the time
a small suite takes. Keep one engine running for tests and point the variable at it, and every run — one
project from the IDE, `dotnet test Wayd.slnx`, or the script — skips the boot.

Start it once, from the image in `SqlServerTestImage.cs` so it matches CI. Choose your own `sa` password; it
needs upper and lower case, a digit and a symbol. The port is published on loopback only.

```bash
docker run --detach --name wayd-test-sqlserver --restart unless-stopped \
  --env ACCEPT_EULA=Y --env MSSQL_SA_PASSWORD='<password>' --env MSSQL_MEMORY_LIMIT_MB=6144 \
  --publish 127.0.0.1:14333:1433 \
  mcr.microsoft.com/mssql/server:2025-CU9-GDR1-ubuntu-24.04
```

On Windows, run the same command in PowerShell with a backtick (`` ` ``) in place of each trailing `\`.

Then set the variable where your IDE's test runner will see it, not only in one terminal:

- **Linux** — a file in `~/.config/environment.d/` (for example `wayd-test.conf`) holding
  `WAYD_TEST_SQLSERVER=Server=127.0.0.1,14333;User Id=sa;Password=<password>;TrustServerCertificate=True`.
  That file expands `$` and treats `\` as an escape, so keep both out of the password. Log out and back in
  for desktop apps to see it; this reaches them only in a session started through systemd (GNOME, KDE, or
  a compositor launched with `uwsm`). Otherwise export the variable from your shell profile and start the IDE
  from a terminal.
- **macOS** — `export WAYD_TEST_SQLSERVER='…'` in `~/.zshrc`, and start the IDE from a terminal, or it
  will not inherit the variable.
- **Windows** — a user environment variable, then restart the IDE and any open terminals:

  ```powershell
  [Environment]::SetEnvironmentVariable('WAYD_TEST_SQLSERVER',
    'Server=127.0.0.1,14333;User Id=sa;Password=<password>;TrustServerCertificate=True', 'User')
  ```

Leave the database out of the connection string; each suite creates its own. The suites change nothing on the
engine apart from their `wayd-test-*` databases. A database is left behind only when a test process is killed
before it finishes, and the next run a day later drops it. Several suites running at once share the engine's
memory, so if early queries time out, lower `INTEGRATION_TEST_PARALLELISM`. When you bump
`SqlServerTestImage.Name`, recreate this container from the new tag.

### Sharing a database

Each collection creates a database of its own on that engine, named `wayd-test-<suite>-<guid>`, and drops it
when the collection ends. A database older than a day with that prefix is from a run that crashed before
dropping it, and the next suite to start drops it. Anything instance-wide — logins, server configuration — is
shared by every suite on the engine, so a fixture must never change it.

Every test class in a collection shares its database and migrated schema, through a collection fixture:

```csharp
[CollectionDefinition(Name)]
public sealed class SqlServerTestCollection : ICollectionFixture<SqlServerDbContextFixture>
{
    public const string Name = "SqlServer integration tests";
}

[Collection(SqlServerTestCollection.Name)]
public sealed class MyIntegrationTests(SqlServerDbContextFixture fixture) { }
```

Put a new class in the project's existing collection. Tests in a collection run one at a time; collections run
in parallel. A collection costs a database and a migration, about a minute locally, and parallel collections only
pay when the tests wait rather than compute: on CI's 4-core runner, splitting the CPU-bound
`Wayd.Web.Api.IntegrationTests` made it slower, so it keeps one SQL Server collection (`ApiTestCollections`). Never
give each class a fixture of its own with `IClassFixture<T>` for a database the class could share; that is a
migration per class.

Tests in a collection **share a database**. Scope assertions to data the test itself created (a fresh `Guid`, a
unique key) rather than assuming an empty schema or querying for "the only row". Nothing outside the database
is per collection: a test may not change process-wide state — an environment variable, a static setting — that
a test in another collection reads, and a host's configuration goes through `UseSetting`, never an environment
variable.

Get a fixture's database with `SqlServerTestDatabase.Create("<suite>")` from `Wayd.Tests.Containers`, rather than
starting a container yourself. It leases the shared engine when there is one, and otherwise the one container
the test process shares (`SqlServerTestServer`), started from the image pinned once as `SqlServerTestImage.Name`.

A migration test needs a database migrated only as far as the migration before the one it tests, so it cannot
use the collection's. In `Wayd.Infrastructure.IntegrationTests`, such a class takes
`IClassFixture<SqlServerMigrationFixture>` and asks it for `MigratedTo(previous)`: the first test migrates a
database and snapshots it, and every later test gets it reverted to that snapshot, in a fraction of a second.
Each such class is a collection of its own, so it runs beside the rest.

`Wayd.Tests.Containers` is referenced only by integration projects, so `Wayd.Tests.Shared` and the unit
projects never depend on Testcontainers.

### Authenticated HTTP requests

`Wayd.Web.Api.IntegrationTests` boots the real API against its database, so a test can call an endpoint
the way a client does. `CreateAuthenticatedClient` creates a local user holding exactly the permissions you
name, signs them in through `POST /api/auth/login`, and returns an `HttpClient` that sends their token:

```csharp
var user = await _factory.CreateAuthenticatedClient(
    ApplicationPermission.NameFor(ApplicationAction.Import, ApplicationResource.StrategicThemes));

var response = await user.Client.PostAsync(route, content, TestContext.Current.CancellationToken);
```

Each call makes a new role and user, so one test's permissions never reach another's. Use it for anything
that belongs to the HTTP layer: status codes, headers, model binding, and the permission attributes. Tests
that only need a handler to run can still dispatch through `IDispatcher` in a scope.

## Test Structure

These conventions keep the suite consistent and easy to scan. New tests should follow them.

### One class per system-under-test, named after the file

Each test class targets a single system-under-test (SUT), and the class name matches its file name. Do **not** merge tests for several SUTs (e.g. multiple command handlers) into one class — give each handler its own `\{Handler\}Tests.cs` containing a class of the same name.

### Arrange / Act / Assert comments

Every test method marks the three phases with `// Arrange`, `// Act`, and `// Assert` comments so the flow reads at a glance. When the setup needs context, append a note to the marker:

```csharp
[Fact]
public async Task Handle_ShouldFail_WhenModelIsActive()
{
    // Arrange — an active model cannot be deleted; the handler's guard should reject it
    // and leave the row in place.
    var model = _faker.AsActiveWsjf();
    _dbContext.ScoringModels.Add(model);
    var command = new DeleteScoringModelCommand(model.Id);

    // Act
    var result = await CreateHandler().Handle(command, TestContext.Current.CancellationToken);

    // Assert
    result.IsFailure.Should().BeTrue();
    _dbContext.SaveChangesCallCount.Should().Be(0);
}
```

### Cancellation tokens

Pass `TestContext.Current.CancellationToken` to **every** method that accepts a `CancellationToken` — both the handler's `Handle(...)` call and any EF assertion queries (`SingleAsync(...)`, `AnyAsync(...)`, etc.). This is the dominant convention across the suite and clears the `xUnit1051` analyzer warning. Avoid `CancellationToken.None`.

## Fake Data

Domain fakers generate realistic test data with Bogus. They live in **each model's own test project**, under a `Data/` folder. Only the `PrivateConstructorFaker<T>` base class lives centrally, in `Wayd.TestData.Core` (namespace `Wayd.TestData.Core`). Test projects reach it transitively through their `Wayd.Tests.Shared` reference, so no extra project reference is needed.

One intentional exception to the colocation rule: **cross-cutting fakers** for types no single domain owns live in `Wayd.Tests.Shared/Data/` — `FeatureFlagFaker`, `OidcProviderFaker`, `PersonalAccessTokenFaker`, `UserFaker`. Reuse these rather than duplicating or relocating them.

```csharp
var faker = new ScoringModelFaker();
var model = faker.Generate();
```

### Faker conventions

- **Per-property `With\{Property\}` builder extensions**, not a single `WithData(...)` with optional parameters. Each extension sets one `RuleFor` and returns the faker for chaining.
- **`With\{Property\}` means "set exactly this value."** Do not skip null values inside the extension. If a nullable property needs to be cleared, `WithDescription(null)` or `WithParentId(null)` should set the generated model's property to null.
- **`As...` state helpers** are for coherent domain states and may update several aligned properties together — e.g. `AsActive()` can set status, date range, and timestamps consistently. If an `As...` helper accepts optional parameters, it should call the relevant `With\{Property\}` method only when the optional value is supplied.
- **Composition helpers** that build child collections through the aggregate's own methods (so invariants and ordering hold) are encouraged — e.g. `AsProposedWith(scales, criteria, outputs)`.
- **Encapsulate shared fixtures as faker extensions**, not a separate `\{Thing\}TestData` holder class. When several test classes need the same realistic entity, add a convenience extension that builds the canonical fixture (e.g. `AsProposedWsjf()` / `AsActiveWsjf()` on `ScoringModelFaker`) and call it from each test. Keep small one-off fixtures inline.

### Fake DbContext

Fake `DbContext` implementations are available for each application area, in the Application test project's `Infrastructure/` folder (`FakeWaydDbContext` and `FakeImportDbContext` in `Wayd.Common.Application.Tests`, `FakeWorkDbContext`, `FakeProjectPortfolioManagementDbContext`, and one for each other module with Application tests), backing each `DbSet` with an in-memory list so handlers can be tested without a database. They track `SaveChangesCallCount`, which assertions use to verify a handler saved (or didn't) as expected. Combine with `NullLogger<T>.Instance` for the handler's logger.

```csharp
private readonly FakeWaydDbContext _dbContext = new();
private readonly Mock<ICurrentUser> _currentUser = new();
private readonly TestingDateTimeProvider _dateTimeProvider = new(new FakeClock(Instant.FromUtc(2026, 1, 15, 9, 30)));
private readonly ScoringModelFaker _faker = new();

private DeleteScoringModelCommandHandler CreateHandler() =>
    new(_dbContext, _currentUser.Object, _dateTimeProvider, NullLogger<DeleteScoringModelCommandHandler>.Instance);
```

A fake runs queries as LINQ-to-Objects, so it cannot catch what only a real provider does: a missing
`.Include` (the fake's navigations are whatever the test set), a projection that does not translate to SQL,
or one save that should span two interfaces. A change that depends on any of these needs a test in the
module's `*.IntegrationTests` project.

## Running Tests

```bash
# All tests (both halves; the integration suites need Docker running)
dotnet test Wayd.slnx

# Only the tests that need no Docker — what CI's unit run covers
./.github/scripts/dotnet-test-projects.sh unit

# Only the Testcontainers suites (Requires=Docker) — what CI's integration jobs cover
./.github/scripts/dotnet-test-projects.sh integration

# One integration shard, as one CI job runs it
./.github/scripts/dotnet-test-projects.sh integration api

# Specific project
dotnet test "Wayd.Services/Wayd.Work/tests/Wayd.Work.Application.Tests/Wayd.Work.Application.Tests.csproj"

# By class name, within one project
dotnet test "<project>" --filter "FullyQualifiedName~ProjectServiceTests"

# By category, within one project (--filter-trait "Category=Unit" is the native xUnit form)
dotnet test "<project>" --filter "Category=Unit"

# Architecture tests
dotnet test Wayd.ArchitectureTests/Wayd.ArchitectureTests.csproj
```

Tests run on Microsoft.Testing.Platform (MTP), opted into by `global.json`; VSTest is not used. Each test
project is its own executable, and any option `dotnet test` does not recognise is passed through to it,
so run `dotnet test "<project>" --help` for the full list (filters, `--coverlet`, `--hangdump`, reports).

A test module that runs zero tests fails with exit code 8. A filter therefore fails on every project it
matches nothing in, so a filtered run across the whole solution fails. Filter one project at a time, or
use the split script above.

### Coverage

`COLLECT_COVERAGE=true ./.github/scripts/dotnet-test-projects.sh <unit|integration>` collects Cobertura
coverage with coverlet (`--coverlet`) into `TestResults/coverage.cobertura.<timestamp>.xml` at the repo
root. The include and exclude rules live in the root `testconfig.json`, which every test project gets
next to its assembly as `<Assembly>.testconfig.json`. A project can replace it with its own `testconfig.json`;
`Wayd.ArchitectureTests` does, to exclude everything, because reflecting over instrumented assemblies
throws `TypeLoadException`.

### Test traits

Four independent axes are available for selecting tests:

| Trait | Values | Meaning |
|---|---|---|
| `Category` | `Unit`, `Integration` | What kind of test it is. Applied automatically per assembly — do not set by hand. |
| `Requires` | `Docker` | Infrastructure it cannot run without; absent when it needs none. Applied automatically per assembly — do not set by hand. |
| `Suite` | `Smoke` | A curated fast pass. Untagged tests are the default regression body. |
| `Area` | `PPM`, `Security`, … | What it covers, cutting across projects. |

Values live as constants in `Wayd.Tests.Shared` (`TestCategories`, `TestRequirements`, `TestSuites`, `TestAreas`). Use
them rather than string literals: in a filter that combines several conditions, a typo in one of them
silently runs fewer tests instead of failing.

## Frontend Tests

```bash
cd Wayd.Web/src/wayd.web.reactclient
npm test               # one run of every suite
npm run test:watch     # reruns affected suites on change
npx vitest run <path>  # one file or folder
npm run test:ci        # what CI runs on a PR
npm run test:coverage  # what CI runs on a merge to main
```

Uses Vitest with React Testing Library. Component suites (`*.test.tsx`) run in jsdom; logic suites (`*.test.ts`) run in node, which skips building a DOM for each file, and one that renders a hook or touches the DOM starts with `// @vitest-environment jsdom`. `src/vitest.setup.ts` holds the module mocks every suite shares (`next/navigation`, the theme hook); `src/vitest.setup.dom.ts` adds the browser shims jsdom lacks, such as `matchMedia` and the grid viewport size. Storage, `dayjs` and the markdown pipeline are real: storage is cleared after each test, and a test that needs a fixed date sets one with `vi.setSystemTime`. A module mock names its module as `vi.mock(import('x'), …)`, so the compiler checks the factory against the real module; a partial mock spreads `await importOriginal()`, and a stub that deliberately falls short of the real type, such as a plain function standing in for an antd component, takes an `as unknown as typeof actual.X` cast with a comment saying why. Nothing a test changes outlives it: every `vi.spyOn` is restored and fake timers are switched back off after each test, so set either up in `beforeEach` or the test itself, never `beforeAll`. Don't silence `console.error` for a whole file; spy on it in the test that expects the error.

PRs run without coverage, since nothing reads it there; only the main-branch build collects it (v8
coverage adds about a tenth to the run). Both the .NET and client coverage numbers are published to that
run's summary page.

The client figure counts every hand-written source file under `src/`, so a file no test loads reports 0%
rather than dropping out. The generated API client (`src/services/api/`), type declarations, and the test files
with their setup and helpers are left out (`coverage.exclude` in `vitest.config.mts`).
