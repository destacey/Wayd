# Data Generation (`wayd-data`)

`wayd-data` is a developer tool that **generates a realistic company** — people and a management tree, a
cross-functional delivery hierarchy, and a full project-portfolio dataset on top of it — and **seeds it into
a Wayd environment through the public HTTP API**. Use it to stand up a believable environment for exploring
features or demoing, without hand-crafting data. Every seed run also exercises the real API end to end, so
it doubles as an integration smoke test.

**Project:** `Wayd.Tools/DataGeneration/src/Wayd.Tools.DataGeneration.Cli` (the executable is `wayd-data`).

:::info Scope
Generates the organization (people + team hierarchy) and the PPM dataset (portfolios, programs, projects,
tasks, strategic themes, and strategic initiatives with KPIs). Use the `org-only` recipe, or `--skip-ppm`,
for the organization on its own.
Planning and work items are not generated. Database **reset** is a separate, out-of-band operation (an
Aspire dashboard command), not part of this tool.
:::

## Quick start

The tool has three verbs: **`generate`** (write CSVs to disk to inspect), **`seed`** (generate and push
through the API), and **`ui`** (build a recipe in a browser). `generate` and `seed` share the same
generation options.

If you would rather not start from a command line, [`wayd-data ui`](#the-ui) opens a page that builds the
recipe for you and shows the command it corresponds to.

:::note `generate` writes files to read, not files to post
The organization files are postable as they stand — every reference in them is a natural key the generator
owns. The PPM files are the generated model: they name portfolios, programs and categories rather than
pointing at ids, because those ids only exist once a run has created the records. `seed` resolves them
stage by stage as it goes; there is no way to write a postable PPM file ahead of a run.
:::

```bash
# Preview: write the CSVs to a folder, no API needed
dotnet run --project Wayd.Tools/DataGeneration/src/Wayd.Tools.DataGeneration.Cli -- \
  generate --value-streams 3 --teams 20 --out ./seed

# Seed a running environment
dotnet run --project Wayd.Tools/DataGeneration/src/Wayd.Tools.DataGeneration.Cli -- \
  seed --api https://localhost:7021 --api-key <token> \
  --company-type tech --value-streams 3 --teams 20
```

The API base URL is shown in the Aspire dashboard when you run the stack
(`cd Wayd.AppHost && dotnet run`).

## Authentication

The tool authenticates with a **Personal Access Token** in the `x-api-key` header. Create one in the app
under **Settings → Personal Access Tokens**, then pass it with `--api-key` or the `WAYD_API_KEY`
environment variable:

```bash
export WAYD_API_KEY=<token>   # or set WAYD_API_KEY=<token> on Windows
dotnet run --project Wayd.Tools/DataGeneration/src/Wayd.Tools.DataGeneration.Cli -- \
  seed --api https://localhost:7021 --value-streams 3 --teams 20
```

No password is ever handled by the tool, and a token is scoped, expiring, and revocable on its own.

:::tip Re-seeding
The import is **additive** and rejects duplicates, so it expects a clean database. To re-seed, reset the
database first (Aspire dashboard → the reset command), then run `seed` again.

A reset takes **your account with it**, not just your tokens. The application's own database seeder creates
roles, not users, and `wayd-data`'s accounts cannot help you here — creating them needs a token, which needs
an account. So the loop back to a working token is:

1. **Reset**, then start the application. With no users in the database it prints a one-time bootstrap token
   to the log; see [First-Run Setup](../first-run-setup.mdx).
2. **Create the first admin** at `<your-app-url>/setup`, or `POST /api/auth/setup` with the token. This
   account is created with no forced password change, so it is usable immediately.
3. **Create a Personal Access Token** under Settings → Personal Access Tokens, or
   `POST /api/user-management/personal-access-tokens`.
4. **Seed** with that token. The seed then creates its own accounts on top of yours — see
   [Sign-ins and roles](#sign-ins-and-roles) — so after this you can sign in as any of the generated
   people as well.

Every step has an HTTP endpoint, so the whole loop can be scripted — the bootstrap token is the only value
that has to come out of the log, and it lasts for the lifetime of that process only.
:::

## Recipes

A **recipe** is a JSON file naming the knobs you care about, so a particular shape of company is something
you name rather than a line of flags you remember. Six ship with the tool:

```
$ wayd-data recipes

  default        A small tech company with a full four-year delivery window.
  demo           A fixed dataset for demos and screenshots.
  enterprise     A large non-delivery-led business.
  large-tech     A scaled product organization.
  org-only       The organization on its own, with no PPM dataset over it.
  startup        A young company: one product line, a handful of teams.
```

Use one with `--recipe <name>`, or point `--recipe` at a file of your own.

:::note
Examples in this section use the short `wayd-data` form. From a checkout that is
`dotnet run --project Wayd.Tools/DataGeneration/src/Wayd.Tools.DataGeneration.Cli -- …`, as above.
:::

```bash
wayd-data generate --recipe large-tech --out ./seed
wayd-data seed --recipe startup --api http://localhost:5150 --api-key $WAYD_API_KEY
```

### The three layers

Values resolve bottom-up, and the top one that states a value wins:

1. **The shipped defaults** (the `default` built-in) — states every knob, so a run always has a complete set.
2. **The recipe you named** — states only what it cares about; anything it leaves out shows the layer below.
3. **The flags you passed** — beats both.

So `--recipe startup --teams 9` gives you the startup shape with nine teams. That last layer is why no
option has a default value any more: an option carrying one reads back as "the user typed this" whether
they did or not, which makes "an explicit flag wins" impossible to implement.

### Writing your own

Start from a built-in rather than a blank file. `recipes show` prints one with its `extends` chain already
resolved, so it is both a worked example of the format and a working starting point:

```bash
wayd-data recipes show large-tech > my-company.json
wayd-data generate --recipe ./my-company.json
```

A recipe states only what it changes and inherits the rest:

```json
{
  "$schema": "https://wayd.dev/schemas/wayd-data/recipe.schema.json",
  "version": 1,
  "extends": "large-tech",
  "description": "Our shape, but with a longer history and no function portfolios.",
  "timeline": { "companyAgeYears": 20, "historyYears": 4 },
  "ppm": { "functionPortfolios": 0 }
}
```

Point `$schema` at the schema (`wayd-data recipes schema` writes it out) and your editor will complete
field names and flag typos as you type. The tool checks the same thing at run time and **rejects a key it
does not recognise**:

```
Recipe error: Recipe 'my-company.json' could not be read: The JSON property 'teemz'
could not be mapped to any .NET member contained in type 'OrganizationRecipe'.
```

That strictness is deliberate. A misspelled key that parses cleanly and does nothing is the worst thing
this format could do — the run succeeds and quietly ignores what you asked for.

### Areas

Each area block carries an `enabled` flag, so switching one off is part of the format rather than another
`--skip-x` flag:

```json
{ "extends": "default", "ppm": { "enabled": false } }
```

That is exactly what the `org-only` built-in is. `--skip-ppm` still works as a shorthand, and only ever
turns the area off — leaving it out never switches an area back on over a recipe that disabled it.

The organization is the exception: it cannot be disabled, and saying so is an error rather than a silent
no-op. Every other area is generated *over* it — portfolios and projects name people by employee number,
and projects are scoped to a team — so a run without it produces nothing at all.

### Sign-ins and roles

A seeded environment used to have hundreds of employees and one account linked to none of them, which made
every PPM rule unreachable: the account you signed in with either administered everything or led nothing.
The seed now creates roles and gives accounts to the people whose authorization actually differs.

Six roles are created, chosen to sit on real seams in the authorization model rather than on job titles:

| Role | What it demonstrates |
|---|---|
| `Read Only` | The baseline — sees everything, changes nothing. |
| `Team Member` | Work items gate on the permission **alone**, with no leadership of the project required. |
| `Project Manager` | The permission reaches every project; **delivery leadership decides which ones actually change**. |
| `Delivery Manager` | The same, one level up — the portfolios and programs above those projects. |
| `Product Manager` | The other model: product management has no `Administer` counterpart, so the claim alone is enough. |
| `PPM Administrator` | The membership bypass. Waives per-record leadership across the whole domain, so it goes to one person. |

Sponsors deliberately get `Read Only`. They are excluded from delivery leadership by design, so an account
that sponsors a portfolio and still cannot change it is the other half of the same rule.

Wayd ships exactly one role — `Admin` — and it carries `Administer ProjectPortfolioManagement`. Seeding
every account as `Admin` would switch off the rules the environment exists to exercise, which is why the
seed creates a spread instead and hands the bypass to almost nobody.

Every account is created with the same password, which the recipe states:

```json
"users": {
  "enabled": true,
  "password": "Test123$"
}
```

One password for all of them is deliberate — switching between people to check a rule is the point. Wayd
prompts each account to change it at first sign-in; that is a client-side prompt rather than something the
API enforces, so the account works immediately either way.

`--skip-users` turns the area off, and `--user-password` overrides the password for one run.

:::note Which employees get an account
The people holding a PPM role — sponsors, owners and managers — plus the executives, which is a few dozen
rather than the whole company. An account that leads nothing behaves like every other account that leads
nothing, so there is little to learn from hundreds of them. The executives are included so an
organization-only run still leaves you a way in.
:::

### The timeline block

`timeline` is the run's clock in serialized form, and the same values described under
[Reproducibility](#reproducibility):

```json
"timeline": {
  "asOf": null,
  "companyAgeYears": 5,
  "teamStructureAgeYears": 2,
  "historyYears": 2,
  "runwayYears": 2
}
```

`asOf: null` anchors on the real today, so data straddles now. `demo` is the only built-in that pins it,
which is what lets a demo dataset be reproduced byte for byte when paired with `--random-seed`.

A recipe never pins the seed. A recipe describes a *shape*, and baking a seed into one would make every
run of it produce the same company — which is what `--random-seed` is for, when you want it.

## The UI

`wayd-data ui` opens a local page for building a recipe: pick a built-in, adjust the knobs, see what it
would generate, and write the CSVs.

```bash
wayd-data ui                       # opens a browser
wayd-data ui --no-browser          # prints the URL instead
wayd-data ui --out ./seed          # where "Write CSVs" writes by default
```

It is a second front end over the same resolver, not a second implementation. Three things follow from
that, and they are the reason it exists in this shape:

- **The form is built from the recipe schema at run time.** Adding an area to the recipe format puts it on
  the page with no change to the page. Hand-written fields would drift the first time the format grew.
- **Generation goes through the same code `generate` runs**, so the two cannot produce different data from
  the same recipe.
- **It shows you the command.** The page displays the equivalent `wayd-data generate …` line, with a copy
  button, beside the recipe JSON. The intent is that the page teaches the CLI rather than replacing it —
  you can stop using the page as soon as you know what to type.

:::note Seeding stays on the command line
The page generates files; it does not seed an environment. Seeding needs a Personal Access Token, and a
browser form is a worse place to keep a credential than a shell that already has one in `WAYD_API_KEY`.
:::

### How it is reached

Bound to a loopback address on a port the operating system picks, and gated by a token generated per run
and carried in the launch URL — the same shape the [Aspire dashboard](../../getting-started/) is opened
with. The page takes the token out of the address bar as soon as it loads and sends it as a header, so it
stops appearing in history or in a screenshot. A request without it gets a 404 rather than a 401, which
tells something that merely found the port as little as possible.

Nothing is served to the network, and nothing is written outside the folder you name.

## Options

Flags beat whatever the recipe said. Defaults below are what the shipped `default` recipe states, not
values baked into the options themselves.

Every knob the recipe format states has a flag here, and a test pairs the two so neither can quietly get
ahead of the other. That is what lets the [UI](#the-ui) print a command that reproduces what is on screen:
anything you can compose in the page, you can also say on a command line.

| Option | Default | Purpose |
|---|---|---|
| `--recipe` | `default` | A built-in recipe name, or a path to a recipe file |
| `--company-age-years` | `5` | How far back the company's history reaches; nothing is generated before it |
| `--team-structure-age-years` | `2` | How long the current team structure has stood — shorter than the company's own age |
| `--history-years` | `2` | Delivery history behind the as-of date |
| `--runway-years` | `2` | Planned work ahead of the as-of date |
| `--company-type`, `-c` | `tech` | `tech` / `balanced` / `enterprise` — sets the share of employees inside the delivery team structure |
| `--delivery-ratio` | (from type) | Override (0..1) for the inside-teams share |
| `--value-streams`, `-v` | `3` | Number of value streams (product lines); larger ones become three-tier |
| `--teams`, `-t` | `18` | Number of leaf delivery teams (overall headcount derives from this) |
| `--former-employees` | `0.08` | Fraction of non-delivery ICs marked former (inactive) |
| `--skip-users` | off | Do not create application roles or sign-ins. A shorthand for a recipe that disables the users area |
| `--user-password` | `Test123$` | The password every generated account is created with |
| `--skip-ppm` | off | Generate only the organization; skip the PPM dataset. A shorthand for the `org-only` recipe |
| `--function-portfolios` | `2` | Cross-cutting business-function portfolios, on top of one per value stream |
| `--concurrent-projects-per-art` | `10` | Projects an ART has *in flight at once*; the total generated is derived from this across the window |
| `--concurrent-programs-per-portfolio` | `5` | Thematic programs a portfolio runs at once; the total generated is derived from this across the window |
| `--random-seed`, `-r` | random | Fixed RNG seed for reproducible output (org **and** PPM) |
| `--as-of` | today | The date the run treats as today, which the whole timeline is anchored on. Pin it *with* `--random-seed` for byte-identical output |
| `--out`, `-o` | `./seed` | (`generate` and `ui`) output directory |
| `--no-browser` | off | (`ui` only) print the URL instead of opening a browser |
| `--api`, `-a` | — | (`seed` only, required) API base URL |
| `--api-key` | `WAYD_API_KEY` | (`seed` only) Personal Access Token |

## What gets generated

The generator builds a coherent company top-down.

### The delivery hierarchy (value stream → ART → team)

Wayd "teams" model the **cross-functional product-delivery structure** (a SAFe-style shape), not the whole
company org chart:

- **Value Stream** — a top-level Team of Teams (a product line).
- **ART** — a mid-level Team of Teams grouping delivery teams.
- **Team** — a leaf delivery team.

Value streams are **mixed by size**: a large one becomes the full three tiers (value stream → ARTs →
teams); a small one collapses to a single ART over its teams.

### Who sits where (staffing)

- **Team** — individual contributors, an **Engineering Manager who is also an IC on that team**, and a
  **Product Manager acting as Product Owner**.
- **ART** — an engineering lead (RTE) and a product lead who lead the ART but sit on no single team.
- **Value Stream** — a VP of Engineering and a VP of Product.
- **Executive** — a CEO with a CTO and CPO. The management tree mirrors the delivery hierarchy
  (team EM → ART lead → VP → CTO/CPO → CEO).

### The rest of the company

Real companies have people outside the delivery structure. `--company-type` sets the split:

| Company type | Inside the team structure | Rest of the company |
|---|---|---|
| `tech` (default) | ~85% | ~15% |
| `balanced` | ~50% | ~50% |
| `enterprise` | ~20% | ~80% |

The non-delivery population (Sales, Customer Support/Success, Marketing, Finance, People, Legal, IT
Operations) has its own management chains and **no team memberships**.

### Realistic details

- **Worker type** — most people are regular `Employee`s; a minority of non-manager ICs are `Contractor`,
  `Contingent Worker`, `Intern`, or `Part-Time`. Every manager is a regular employee.
- **Timeline** — the company is modeled as ~5 years old (hire dates span up to five years back); the current
  team structure is ~2 years old (team active dates within two years).
- **Former employees** — some non-delivery ICs are inactive (`--former-employees`). Inactive people are
  never on a team.

### The PPM dataset (portfolios → programs → projects → tasks)

Unless `--skip-ppm` is passed, the generator layers a full **project-portfolio-management** dataset on top
of the org. The two structures are kept **independent** — the *delivery* hierarchy (value stream → ART →
team) decides who builds the work, while the *investment* hierarchy (portfolio → program → project) decides
how it's funded and grouped — and they meet only at the **project**, where funded work is staffed from
delivery teams:

- **Portfolios** — one per **value stream** (named after its domain, e.g. "Payments Portfolio"), plus a
  couple of cross-cutting **business-function** portfolios (`--function-portfolios`) that pull projects from
  teams across value streams. Function portfolios draw from a single naming style per company (business
  function, business unit, strategic, technology, investment-based, or product-based) so they read
  coherently.
- **Programs** — a portfolio's **thematic groupings of projects** (Modernization, Integrations,
  Client-Driven, Growth & Scale, Automation & AI, Platform & Reliability). A program is an *investment*
  structure, **independent of the delivery hierarchy** — it has nothing to do with ARTs. Each portfolio runs
  several concurrently (`--concurrent-programs-per-portfolio`), each 1–3 years long, spread across the window
  so some have finished, some are active, and some lie ahead. A project is sorted into a program by the kind
  of work it is (its leading verb — "Migrate" → Modernization, "Integrate" → Integrations, …), and only into
  a program whose window covers the project's; a minority of projects stay portfolio-direct (standalone).
- **Projects** — **ART-scoped and multi-team**, matching how delivery actually works: a project is a subset
  of an ART's teams collaborating, each owning their own features. Most projects span **two to five teams**;
  a single-team project is the minority, and about **one in ten reaches across ARTs** within the value
  stream. One participating team is the **owning team** — it provides the Engineering Manager (owner/manager)
  and Product Owner (sponsor) and decides the program placement — and the project's members are the **union**
  of everyone across the participating teams. Each project gets the shared **Standard Delivery** lifecycle
  and an expenditure category. Volume is set by `--concurrent-projects-per-art` (how many an ART runs at
  once); the total is derived from the four-year window and typical 2–9-month durations, so an ART
  accumulates a deep history and a full runway rather than a handful of projects.
- **Project tasks** — a dense work breakdown (stages → root tasks → child tasks, plus a milestone per
  stage) for every project that has started; proposed and future projects have none yet. Each **stage's
  status** is rolled up from its tasks (all done → Completed, some in flight → In Progress, none started →
  Not Started) and imported as data — the stage-status import applies exactly what the generator computes and
  never derives it server-side, so a real client keeps full control of stage status.
- **Strategic themes** — a handful of active themes, tagged onto programs and projects.
- **Strategic initiatives + KPIs** — one per portfolio, linking a few of its projects, each with a couple
  of KPIs.

**The four-year timeline.** Work spans two years of history and a two-year runway from today, and each
item's status follows its position on that window: finished in the past (**Completed**, a few
**Canceled**), in flight around today (**Active**), and not-yet-started in the future (**Proposed** /
**Approved**). Task progress and status track the same timeline.

Each portfolio, program and project also carries the dates it *moved* — `CreatedOn`, and `ActivatedOn` and
`ClosedOn` where its status reached them — which are separate from the `Start`/`End` timeline it plans to run
over. The import rejects a date for a status a record never reached, so the generator emits exactly the ones
each status allows: a proposed project gets no activation date, and only a closed one gets a closing date.
Records are proposed a few weeks to a few months before they activate, which for the earliest of them is
before the window itself — work proposed before the window is exactly what a creation date is for.

For projects this is what dates the [status history](../../user-guide/ppm/projects.mdx): every replayed transition is
stamped from these columns, so a seeded project's history reads as its own timeline rather than as the moment
the seed ran. Portfolios and programs record no transition dates yet, so theirs are validated and then go no
further than picking which transitions to replay.

**Settings prerequisites.** Expenditure categories and the project lifecycle are **settings**, not imports.
The `seed` verb bootstraps them through the normal settings API (create-or-get by name, and it activates the
lifecycle) before importing projects, which reference them by id. They are not written as CSV by
`generate`.

:::note Why some historical work is "finalized" separately
The domain only lets work be **added** to an active program or portfolio, but only lets one be **closed**
once everything inside it is closed. So historically-complete programs and portfolios are imported active
and then closed by a final `finalize` pass, after their contents exist. The generator emits the finalize
rows automatically; you'll see a "Finalizing …" line at the end of a seed run when any apply.
:::

## Reproducibility

Every run resolves a concrete seed (random when `--random-seed` is omitted) and prints it:

```
Using seed 193051458 as of 2026-06-15 (pass --random-seed 193051458 --as-of 2026-06-15 to reproduce this data).
```

Re-run with **both** of those to reproduce byte-identical data, for a given build of the tool. The seed pins
the randomness, not the algorithm: if the generator changes, the same seed produces different data.

Both are needed because they pin different things, and either alone reproduces nothing. `--random-seed` fixes
the draws; `--as-of` fixes the date the whole timeline hangs off. Leave `--as-of` out and it defaults to
today, which is usually what you want — generated data straddles now, so there is history behind and runway
ahead — but it also means tomorrow's run places every record a day further along, and flips anything that
crossed today from active to complete.

:::note What "reproducible" means here
The seed reproduces the **generated data** — the same names, emails, employee numbers, team codes, and
hierarchy. It does **not** reproduce the database primary keys. Wayd assigns IDs (and other server-side
keys) when the rows are created through the API, so seeding the same data twice yields different database
IDs each time. Use the generated business keys (employee number, team code) to correlate across runs, not
the database IDs.
:::

## How it works (and why)

The tool **never touches the database directly** — it POSTs CSV to the API's import endpoints (the same
endpoints documented in the [Organization](../../user-guide/organizations/bulk-import.mdx) and
[PPM](../../user-guide/ppm/bulk-import.mdx) Bulk Import guides), and each import handler creates rows
**through the owning domain's commands**. This is deliberate: Wayd domains keep
aligned local copies of shared concepts (creating an `Organization.Team` replicates it into the PPM,
Planning, and Work read models via domain events). Going through the domain path means one `SaveChanges`
fires those events, so the copies stay consistent — a direct insert would leave them empty. A useful side
effect: seeding proves the real API and cross-domain wiring work.

### Areas, and the order they run in

A seed is a set of **areas**, each one a unit that reads what it needs, writes its file, waits for the
import to finish, and publishes the ids it created. An area declares what it depends on; the runner
derives the order from those declarations rather than from a list someone maintains by hand.

That indirection earns its place because the order is not a preference. A program cannot be created before
its portfolio, staffing resolves roles it does not create, and the finalize pass can only close a program
once its projects are closed. Stating the dependency keeps it from drifting away from the ordering as
areas are added — and adding one means declaring what it needs, not finding the right line to insert a
call at.

Today's areas resolve to:

```
employees → teams → team hierarchy → roles (created as needed) → team staffing
  → expenditure categories + lifecycle (settings bootstrap)
  → strategic themes → portfolios → programs → projects → project tasks → project stage statuses
  → strategic initiatives (+ KPIs) → finalize (close historical programs/portfolios)
```

### One area can be more than one file

An import rejects a file past its row cap outright, and the atomic ones — which is all of the PPM imports —
cap at 10,000 rows. An atomic import cannot be split server-side, so that cap is the only thing bounding a
run that is applied as one transaction; it is the server's guard against an arbitrary client, and the seed
is a client like any other.

The task file is the one that passes it: a dense breakdown across a few hundred projects runs to around
12,000 rows at default options. So that area sends several files, and the run log says so:

```
Importing 11573 project tasks in 2 batch(es)...
  batch 1 of 2: 7988 tasks
  batch 2 of 2: 3585 tasks
```

The split falls on **project boundaries**, and that is not a convenience. The task import is whole-set
because rows within a project are not independent — a child names its parent by that parent's `ImportId` in
the same file, and the per-project task number advances as rows are applied. Cutting a project across two
files hands the second one a child whose parent it never saw. A single project larger than the cap is left
whole and rejected rather than split, because a named failure beats a file that imports a broken tree.

### Post, wait, read back, substitute

An import answers with its **run**, having waited a few seconds for it: a small file comes back finished,
a large one still queued or running — taken, not applied. Each area therefore polls that run to
completion and reads its row outcomes back before the next area writes anything, because those outcomes
are where the created ids are.

Each row is submitted under an `ImportId` set to the generator's own handle for that record — a
portfolio's name, a project's key — so the ids come back keyed the way the next file already refers to
them, with no second mapping to keep in step.

Each import is all-or-nothing, and the seed aborts on anything short of a clean run, naming the rows that
were rejected by their import id. References resolve by natural key where a record has one — employee
number, team code, project key — and by id otherwise. Pass `--skip-ppm` to stop after the organization;
nothing in the organization depends on a resolved id, so that path is unaffected by any of this.

## Data conventions

Generated data is fictional — RFC-reserved domains (`acme.example`) and invented names and numbers. Never
seed values copied from real payloads or third-party fixtures.
