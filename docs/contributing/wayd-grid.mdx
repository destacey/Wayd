# WaydGrid

`WaydGrid` is Wayd's house data-grid component, built on [TanStack Table](https://tanstack.com/table). It's the single grid used across the app — flat lists, grouped headers, and hierarchical (tree) data — with a consistent toolbar, Excel-style column filters, sorting, column sizing/visibility/pinning/reordering, always-on row virtualization, CSV export, and (opt-in) inline editing and drag-and-drop.

Import it from the barrel:

```typescript
import { WaydGrid, createActionsColumn } from '@/src/components/common/wayd-grid'
import type { ColumnDef } from '@/src/components/common/wayd-grid-core'
```

:::warning[Import table types from `wayd-grid-core`]
TanStack Table v9 puts a features generic first on every public type (`ColumnDef<TFeatures, TData, TValue>`), so a `ColumnDef<Widget>` imported from `@tanstack/react-table` binds the row type to the wrong slot and fails to compile. `@/src/components/common/wayd-grid-core` re-exports `ColumnDef`, `Row`, `Column`, `Cell`, `Header`, `Table` and the rest with the grid's feature set already bound — import them from there.
:::

:::tip[Always use `WaydGrid`]
Never reach for Ant Design's `Table` or raw TanStack Table directly. `WaydGrid` is the seam that keeps grids consistent and lets us swap the engine once. Columns are plain TanStack [`ColumnDef`](https://tanstack.com/table/latest/docs/api/core/column-def)s, extended with a small `meta` object (see [Column meta](#column-meta)).
:::

## Minimal example

A read-only grid needs only `columns` and `data`:

```tsx
const columns: ColumnDef<Widget, any>[] = [
  { id: 'name', accessorKey: 'name', header: 'Name', size: 250 },
  { id: 'status', accessorKey: 'status', header: 'Status' },
]

<WaydGrid columns={columns} data={widgets} isLoading={isLoading} />
```

`data` may be `undefined` while a query is loading — the grid treats it as empty (no crash). Provide `isLoading` to show the spinner.

## Variants

Start by picking a variant — it presets the toolbar and filtering flags below for the two situations grids are actually used in.

| | `simple` | `advanced` (default) |
| --- | --- | --- |
| Toolbar | Hidden | Search, row count, refresh, clear, export, help |
| Column filters | Off | Popup + floating filter row |
| Column menu (sort/pin/autosize) | On | On |
| Height | Fits its rows | Fills the remaining viewport |
| Layout persistence | Don't set `persistStateKey` | Opt-in via `persistStateKey` |
| Row virtualization | On | On |
| Use for | A record's own data, under ~25 rows | List pages and exploration |

**Choose by the question the user is asking.** *"What is on this record?"* → `simple`. *"Which of these do I want?"* → `advanced`.

```tsx
<WaydGrid variant="simple" columns={columns} data={projects} />
```

Individual flags still override the variant, so `variant="simple"` plus `includeColumnFilters` is valid for the rare section that needs one thing back. A `simple` grid never renders the toolbar, so the toolbar's own props — `includeGlobalSearch`, `includeExportButton`, `onRefresh`, `leftSlot`, `rightSlot`, `actionsSlot`, `helpContent` — have no effect on it. Prefer the plain variant where you can — a section grid carrying a full toolbar competes with the page's own chrome.

See **[Record Pages](./record-pages.mdx#grids-inside-sections)** for how this fits the record page structure.

### On small screens

The grid has no breakpoint behaviour of its own: both variants render the same table at every width, and a table wider than its container scrolls horizontally inside the grid's body.

Two traps either way: a wide grid must scroll inside **its own** container, never the page body; and the grid needs a measurable height — it renders zero rows in an unconstrained `<Flex vertical>` parent. Keep it a block-level child, as `src/app/account/profile/claims-grid.tsx` does.

## Feature flags at a glance

Most functionality is **on by default**; you turn things _off_ with a prop, or turn opt-in behaviour _on_ by supplying its handler. This table is the quick reference for "how do I enable/disable X".

Where a variant sets a flag, that is the starting point — the defaults below describe `variant="advanced"`.

| Capability | Default | How to change it |
| --- | --- | --- |
| Global quick-search box | On | `includeGlobalSearch={false}` to hide |
| CSV export button | On | `includeExportButton={false}` to hide; `csvFileName="..."` names the file |
| Per-column filters (popup) | On | `includeColumnFilters={false}` to disable all column filtering UI |
| Floating filter row (under headers) | On | `includeFloatingFilters={false}` (ignored when `includeColumnFilters={false}`) |
| Column sizing (resize handles) | On | Per column: `enableResizing: false` in the def |
| Column sorting | On | Per column: `enableSorting: false` in the def |
| Column show/hide (Choose Columns) | On | Per column: `enableHiding: false`; withhold reactively with `meta.unavailable`; start hidden with `meta.hiddenByDefault` |
| Column pinning (⋮ menu → Pin) | On | Per column: `enablePinning: false` |
| **Column reordering** (drag headers) | On | Auto-disabled on grouped-header grids; per column: `meta.enableReordering: false` |
| **Column layout persistence** | Off | Provide `persistStateKey="..."` to turn it on |
| Row virtualization | On (always) | Not configurable — the visible window plus overscan is mounted |
| Initial sort on mount | Off | `initialSorting={[{ id: 'name', desc: false }]}` |
| Toolbar refresh button | Off | Provide `onRefresh={() => refetch()}` |
| Hidden `Id` column (for import files) | On when rows carry an `id` | `includeIdColumn={false}` when `id` is a client-side row key |
| Row activation (open a row) | Off | Provide `onRowActivate` |
| Row selection | Off | Provide `rowSelection` + `onRowSelectionChange` |
| Row grouping | Off | Provide `grouping` |
| Tree mode | Off | Provide `getSubRows` |
| Row-reorder drag-and-drop (flat) | Off | Provide `onRowReorder` + `getRowId`, and render a `DragHandleCell` |
| Reparenting drag-and-drop (tree) | Off | Provide `enableDragAndDrop` + `onNodeMove` |
| Cell editing | Off | Provide `onCommit` and give columns a `meta.editor` (see [Editing cells](#editing-cells)) |
| Row-level inline editing (being replaced) | Off | Provide `editingConfig` |

## Core props

```tsx
<WaydGrid<Widget>
  columns={columns}          // ColumnDef[] or (ctx) => ColumnDef[]
  data={widgets}             // Widget[] | undefined
  isLoading={isLoading}
  onRefresh={() => refetch()}        // shows the toolbar refresh button
  emptyMessage="No widgets found"    // default 'No records found'
  csvFileName="widgets"              // CSV download name prefix; default 'grid-export'
  persistStateKey="ppm-widgets"      // opt-in column persistence (see below)
  initialSorting={[{ id: 'name', desc: false }]}
  height={480}                       // fixed px; omit to auto-size (see below)
  rightSlot={<MyToolbarControls />}  // custom toolbar content (far right)
  leftSlot={<CreateButton />}        // custom toolbar content (left)
/>
```

- **`columns`** can be a function `(context) => ColumnDef[]` when the defs need editing/DnD/draft state (see [Tree mode & editing](#tree-mode--editing)).
- **`height`** omitted → an `advanced` grid auto-sizes to fill the remaining viewport height (ag-grid style); a `simple` grid sizes to its rows. Pass a number for a fixed height.
- **`leftSlot` / `rightSlot`** inject custom toolbar content; `actionsSlot` sits just before the export button, for a grid-specific toggle; `helpContent` fills a help popover. `leftSlot` may also be a function of the `GridColumnContext`, for a Create button that adds a draft row.
- **`getRowId`** supplies a stable row id (required for `onRowReorder`); it falls back to `row.original.id`, then a TanStack index id.
- **`onDisplayedRowsChange`** fires with the post-filter/sort rows whenever that set changes — for deriving external UI (e.g. a chart) from the grid.
- **`ref`** exposes a `WaydGridHandle`: the TanStack `table`, the editing `selectedRowId`, and `getDisplayedRows()`.
- **`includeIdColumn`** (default `true`) appends a hidden `Id` column when the rows carry an `id` and no column claims it, so a user can show it through Choose Columns and export the ids an import file needs. Pass `false` when `id` is a client-side row key rather than a Wayd record id. Its column id is exported as `ID_COLUMN_ID`.

### Opening a row

`onRowActivate` makes whole rows openable — click, or Enter/Space on any of the row's cells (see [Keyboard and screen readers](#keyboard-and-screen-readers)) — so a list is keyboard-navigable without a link in every primary cell. Clicks on links, buttons, inputs, and anything marked `data-row-activate="ignore"` are left alone, so an actions dropdown inside the row still just opens. Pass `activatedRowId` (matched against `getRowId`) to highlight the open row, and `getRowActivateLabel` to give each row a short accessible name. Flat mode only: tree mode spends the row click on inline editing. A list–detail layout is the reference consumer (see [Record Pages](./record-pages.mdx#does-it-get-a-record-page-at-all)).

### Keyboard and screen readers

Every WaydGrid is keyboard-navigable with nothing to configure. The body follows the WAI-ARIA grid pattern: one cell holds the body's single Tab stop (roving `tabIndex`), and the keys move it. The header keeps its own controls — a sortable column heading, the filter triggers and the `⋮` menus are each a Tab stop, and Enter or Space on a heading sorts it. Header cells drop dnd-kit's keyboard drag; columns reorder by keyboard through Choose Columns.

| Key | Moves or does |
| --- | --- |
| Arrow keys | One cell, stopping at the edges |
| Home / End | First / last cell in the row; with Ctrl (Cmd), first / last cell in the grid |
| Page Up / Page Down | A viewport of rows |
| → / ← in the tree column | Expand / collapse a tree row; ← on a child moves to its parent. On a group heading, any column |
| Enter / Space | Activate the row (`onRowActivate`), or toggle a group heading |
| Enter / F2 | Otherwise: open the cell's editor when the column has one (see [Editing cells](#editing-cells) for the keys while it is open), else focus the cell's own control (a link first, never an expand toggle). Escape from that control returns to the cell |
| Shift+F10 / Menu key | Click the row's element marked `data-row-actions` |
| Tab / Shift+Tab | Leave the body — from a cell or from a control inside one |

- **Columns follow the screen**: the cursor walks the visible leaf columns left-pinned, centre, right-pinned, so reordering and pinning are respected.
- **The tree column** is the one with `meta.treeColumn: true` — the column holding the caret. Without one, the first visible column is.
- **Controls in cells take `tabIndex={-1}`**; Enter or F2 reaches them. `createActionsColumn` does this and marks its button `data-row-actions`; a hand-built row menu should do the same. One that is missed (a `next/link` cell, a drag handle) does not break the single Tab stop: tabbing in onto it lands on the active cell, and Tab from it leaves the body.
- **Keys inside a control are its own.** The body handles a key only when a cell itself has focus (Escape and Tab aside), never in the row being edited inline, and never from a portal — React bubbles a menu's or modal's events through the component tree, so the handlers check the event came from the body's own DOM.
- **Virtualization**: while focus is in the body, the focused row stays rendered when scrolled away, so it keeps DOM focus. When focus is elsewhere and the active row scrolls out, the first rendered row takes the Tab stop.
- **Tab out** works by focusing a sentinel just past (or before) the body during keydown; the browser's own Tab step then runs from there.
- **When the active row goes away** (a cancelled draft, a deleted or filtered-out row) the Tab stop stays at the same position, on whichever row is there now.
- **Semantics**: the header and body tables are presentational and the area wrapping them is one `grid` (`treegrid` in tree mode) with `aria-rowcount` and `aria-colcount`. A grid owns only rows, so the loading/empty message renders as a row, and the chart pane (which repeats the rows' dates and is pointer-only) is `aria-hidden`. Rows carry `aria-rowindex` (header rows included), cells `aria-colindex`, headers `aria-sort`, tree rows `aria-level` and `aria-expanded`. Pass `aria-label` when the page has more than one grid or no heading naming it.

### Selecting rows

`rowSelection` and `onRowSelectionChange` are controlled TanStack row-selection state. Supplying them turns on `row.getIsSelected()`, `row.toggleSelected()`, and the table's select-all handlers, so a consumer renders its own checkbox column against the table rather than tracking selection itself. Select-all covers the filtered rows. `getIsSomeRowsSelected()` means "at least one", so an indeterminate header checkbox needs `!getIsAllRowsSelected() && getIsSomeRowsSelected()`.

## Columns

Columns are TanStack `ColumnDef`s. The most common shape:

```tsx
{
  id: 'status',
  accessorKey: 'status',        // supports dotted paths: 'status.name'
  header: 'Status',             // keep this a plain string — CSV export and the
                                //   column chooser read it
  size: 120,                    // px; also resizable at runtime
  meta: { /* WaydGrid extras — see below */ },
}
```

### Column meta

`meta` is TanStack's per-column bag, augmented with WaydGrid fields (`WaydGridColumnMeta`, strongly typed everywhere):

| `meta` field | Purpose |
| --- | --- |
| `columnType` | Declarative type preset: `'yesNo'`, `'dateOnly'`, `'dateTime'` (see [Column types](#column-types)) |
| `unavailable` | Withholds the column from this user — typically `!canUpdate`. Hidden, absent from Choose Columns, and beats any saved choice, so a permission can't be worked around by unhiding. Reactive: flip the expression and the column returns with its size, pinning and order |
| `hiddenByDefault` | Starts the column hidden but leaves it in Choose Columns, so the user owns it from there. A user's choice wins; Reset Columns returns it to hidden |
| `filterType` | Filter/data type: `'text' \| 'number' \| 'date' \| 'dateTime' \| 'set'` (aliases `'select'`→`set`, `'numericRange'`→`number`). Defaults to `'text'` |
| `filterOptions` | `{ label, value }[]` for a `set` filter (stable order + labels) |
| `filterEnableSet` | On a text column, also offer the Excel-style checkbox set filter alongside the text filter |
| `multiValues` | `(row) => string[]` for a column whose row holds several values; the set filter lists the individual values read from each row, so a value containing a comma stays whole. `createCsvColumn` sets it (see [Multi-value columns](#multi-value-columns)) |
| `filterPlaceholder` | Placeholder for text and number filter inputs |
| `align` | `'left' \| 'right'` — override numeric right-alignment of body cells |
| `headerTooltip` | Tooltip on the header label (keep `header` a plain string) |
| `maxFilterConditions` | Cap AND/OR conditions in the filter popup (default 5) |
| `enableReordering` | Set `false` so the column can't be dragged to reorder (and rejects drops). Such a column also gets no `⋮` menu. Used by the actions column |
| `treeColumn` | Tree mode: the column showing the expand caret, where → and ← expand and collapse rows. Defaults to the first visible column. With cell editing, its commit is what creates a draft row |
| `editor` | Makes the column's cells editable in place (see [Editing cells](#editing-cells)) |
| `enableExport` | `false` excludes the column from CSV |
| `exportHeader` / `exportFormatter` | Override the CSV header text / format each value |

### Column types

Instead of hand-wiring cell formatting + filter config, declare a type:

```tsx
{ id: 'active', accessorKey: 'isActive', header: 'Active', meta: { columnType: 'yesNo' } }
{ id: 'due', accessorKey: 'dueDate', header: 'Due', meta: { columnType: 'dateOnly' } }
{ id: 'created', accessorKey: 'createdOn', header: 'Created', meta: { columnType: 'dateTime' } }
```

- **`yesNo`** — boolean → "Yes"/"No" for both display and the set filter.
- **`dateOnly` / `dateTime`** — formatted for display while the raw value drives chronological sort and the date filter.

Explicit column fields always win over a type's defaults. The formatters behind the date types are exported as `formatDateOnly` and `formatDateTime`, and the yes/no labels as `YES` and `NO`.

### Multi-value columns

A column whose data is several values — a comma-separated string or an array — uses `createCsvColumn`. It renders each value as a tag (`TagListCell`), filters with a set panel that matches on individual values (a row matches if it shares any selected value), and builds that panel's options from the live data, so no option list is passed:

```tsx
createCsvColumn<ProjectListDto>({
  id: 'projectManagers',
  header: 'PMs',
  getValues: (row) => getSortedNameList(row.projectManagers ?? []),
})
```

Omit `getValues` for a plain comma-separated string column; the factory reads `row[id]` and splits it with `splitCsv`.

### Link and tag cells

Cells that link to a record use the shared renderers from the barrel rather than hand-built links: `renderTeamLink`, `renderProjectLink`, `renderPortfolioLink`, `renderProgramLink`, `renderPlanningIntervalLink`, `renderWorkspaceLink`, `renderProductLink`, `renderVersionLink`, `renderReleaseLink`, `renderSprintLink`, `renderUserLink`, `renderWorkItemLink`, and `renderAssignedToLink`. `renderWorkStatusTag` and `renderDependencyHealthTag` render status tags. Each takes the domain object, not the cell context, and returns `null` for a missing value: `cell: ({ row }) => renderTeamLink(row.original.team)`.

### The actions column

Row action menus use the shared `createActionsColumn` helper — a fixed-width (`ACTIONS_COLUMN_SIZE`, 50px) `⋯` dropdown that renders nothing for rows with no items, always holds its position (never sorted, filtered, resized, or reordered), and hides itself when the user can't act on any row:

```tsx
createActionsColumn<Widget>({
  unavailable: !canManage,          // withhold the column entirely when unusable
  ariaLabel: 'Widget actions',
  getItems: (widget) => [
    canEdit && { key: 'edit', label: 'Edit', onClick: () => edit(widget) },
    canDelete && { key: 'delete', label: 'Delete', danger: true, onClick: () => remove(widget) },
  ].filter(Boolean) as ItemType[],
})
```

`id` defaults to `'actions'` and `ariaLabel` to `'Row actions'`.

`leading` renders a node immediately before the `⋯` in the same cell — a row's grab handle, in
practice. Sharing the cell keeps a whole column's width from going to one icon and keeps everything
that acts on a row in one place. Widen the column with `size` when you pass one; see
[Tree mode & editing](#tree-mode--editing) for the handle itself.

## Filtering, sorting & the column menu

These come for free — no wiring beyond the column defs:

- **Global quick-search** filters across every column with an accessor (opt a column out with `enableGlobalFilter: false`).
- **Per-column filters** — an Excel-style popup per column (text/number/date conditions, or a checkbox set list), plus a compact floating-filter row under the headers. The filter UI is inferred from the data or set explicitly via `meta.filterType`.
- **Sorting** — click a header to sort; Ctrl/⌘-click adds a column to a multi-sort.
- **The `⋮` column menu** on each header offers: Sort, Pin Column (left/right/none), Autosize (this column / all columns), Choose Columns (when any column can be hidden), and **Reset Columns**.

**Reset Columns** restores the columns' default sizing, visibility, pinning, **and order** — it deliberately does _not_ clear sorting or filters (the toolbar's Clear button does that).

## Server-paged lists

A grid over a list that pages on the server (`PagedResponse<T>`, see [Paging](./api.mdx#paging)) holds one page,
so it gets its page controls from `WaydGridPager` in the toolbar's `rightSlot`, with `useGridPaging` holding the
page and size it requests:

```tsx
const paging = useGridPaging()
const { data } = useGetJobsQuery({ state, page: paging.page, pageSize: paging.pageSize })
paging.keepInRange(data?.totalPages)

<WaydGrid
  data={data?.items}
  rightSlot={<WaydGridPager paging={paging} totalCount={data?.totalCount} noun="jobs" />}
  …
/>
```

- **Call `keepInRange` during render** with the response's `totalPages`, so a list that shrinks while someone
  reads its last page (jobs finishing, messages replayed) moves back to the page that is now last.
- **Call `resetPage` when a filter sent to the server changes**: page 4 of one filter is not page 4 of another.
  Changing the page size goes back to the first page on its own.
- **Pass `currentData` as the rows and `data` to the pager.** RTK Query's `data` is the last answer for any
  page, so passing it as the rows shows the previous page under the new page's range while the next one
  loads; `currentData` is empty until it arrives. Show loading only while there is no `currentData`, so a
  poll of the same page does not flash.
- **Leave out `initialSorting`.** The page arrives in the list's own order, and sorting it in the browser
  reorders only that page: with jobs that run soonest first, "latest first" would put each page backwards
  against the next.
- **The grid's sorting, search, filters and CSV export act on the page it holds**, not the list. Offer a filter
  the API takes as a request parameter (a `Segmented` over states, as the jobs and import rows grids do) rather
  than leaving the reader to filter a page.

## Column reordering

Reordering is **on by default**. The whole header cell is the drag handle — grab a header and drag it left/right to reorder. A plain click still sorts (a drag only starts after a few pixels of movement); the resize edge, filter icon, and `⋮` menu don't trigger a drag. Columns can also be reordered by dragging rows in the **Choose Columns** modal.

Rules:

- Reordering happens **within a section**: unpinned columns reorder among themselves, and each pinned side (left/right) reorders within itself. Dragging never pins or unpins — that's the `⋮` menu's job.
- **Grouped-header grids** (defs with a `columns` band) disable reordering, so bands can't be split.
- A column can opt out with `meta.enableReordering: false` (the actions column does this automatically).

The order is persisted alongside the rest of the column layout when `persistStateKey` is set (see below).

## Column layout persistence

Persistence is **opt-in**: give the grid a `persistStateKey` and it saves the user's **column sizing, show/hide choices, pinning, and order** to this browser's `localStorage`, restoring them on the next visit.

```tsx
<WaydGrid columns={columns} data={data} persistStateKey="ppm-projects" />
```

- **Sorting, filters, and search are _not_ persisted** — they're session-only.
- A pristine or reset grid stores nothing (the entry is removed), so **Reset Columns** also clears the saved layout.
- Persisted state that references removed columns is ignored; columns added later appear at their def position.

### Choosing a key

`persistStateKey` is **per page context**, not per component — a stable, human-readable, route-independent kebab-case string, e.g. `'ppm-projects'`, `'settings-feature-flags'`, `'team-backlog'`. Two grids that should share a layout use the same key; two that shouldn't must differ.

Shared grid components (used on more than one page) should expose `persistStateKey` as a pass-through prop so each page supplies its own key, rather than hardcoding one.

Stored under `wayd-grid:{persistStateKey}:v2`; a `v1` entry is migrated on load. Give a **visible** column a plain-string `header` (or a `meta.exportHeader`) so it appears in the Choose Columns list — a column with neither is left out.

### The device-wide controls

Two account-level controls (**Account → Preferences → Grids**) cover every persisted grid automatically — no per-grid wiring:

- **Remember column layouts** — the kill switch. When off, grids neither save nor restore layouts; existing saved layouts are kept and re-apply when it's turned back on.
- **Reset all grid layouts** — deletes every saved layout on this device.

These act on this browser only (layouts live in `localStorage`, not on the server). The barrel exports what the page uses: `GRID_PERSISTENCE_ENABLED_KEY` (the switch, absent meaning on) and `clearAllGridColumnState()`. A grid reads the switch when it mounts, so a change applies on the next visit to a grid.

## Tree mode & editing

Providing `getSubRows` turns on **tree mode**: rows expand/collapse, and a filter match keeps the ancestor chain visible. Every node starts expanded; pass `initialExpanded={false}` for a list whose parents are rollups of their children. Layered on top of tree mode are optional reparenting drag-and-drop, inline editing, and draft rows.

```tsx
<WaydGrid<WorkItemTreeNode>
  data={rootNodes}
  getSubRows={(node) => node.children}
  columns={(ctx) => buildColumns(ctx)}   // function form: reads editing/DnD state
  enableDragAndDrop
  onNodeMove={async (nodeId, parentId, order) => reparent(nodeId, parentId, order)}
  moveValidator={myMoveValidator}
  editingConfig={editingConfig}
/>
```

- **Flat row reorder**: instead of `getSubRows`, provide `onRowReorder` (and `getRowId`) for a draggable flat list. Dragging auto-disables while the grid is sorted, filtered, searched, loading, or editing — the displayed order isn't the data order then, and a drop would write a sequence the reader never saw.
  - The grid supplies the mechanics but not the grip: render the shared **`DragHandleCell`** to give a row one, passing `context.isDragEnabled` (so it greys out when dragging is off) and a `disabledTooltip` naming the records in your own words. It goes in the actions column's `leading` slot. This needs the `columns` **function** form, since that is what receives the `GridColumnContext`.
  - `onRowReorder` hands you `orderedData` — every displayed row in post-drop order — so send the whole list to a reorder endpoint rather than one row and a position. Positions are relative, so a partial update leaves the rows it omits overlapping the ones it moved.
- **Reparenting DnD** (tree): `enableDragAndDrop` + `onNodeMove`; supply a `moveValidator` for domain rules and `onMoveRejected` to surface a reason.
- **Editing**: see [Editing cells](#editing-cells). The older row-level path, `editingConfig` (`GridInlineEditingConfig`), has no consumers; prefer cell editing. It wins when a grid passes both. The `columns` function receives a `GridColumnContext` with the editing/DnD/draft state so cells can render drag handles and Create buttons reactively.

These features are involved — read the JSDoc on `WaydGridProps` in [`types.ts`](https://github.com/destacey/Wayd/blob/main/Wayd.Web/src/wayd.web.reactclient/src/components/common/wayd-grid/types.ts) and follow an existing consumer when wiring them — `app/planning/roadmaps/_components/roadmap-items-grid.tsx` uses cell editing (its editors are in `roadmap-items-grid.editors.tsx`), reparenting drag-and-drop and drafts; `app/ppm/projects/_components/project-plan-table.tsx` adds bar drags through `commitCells` and the row-action keys (its editors are in `project-plan-table.editors.tsx`); `project-work-items-tree-grid.tsx` beside it is a read-only tree.

### Editing cells

A grid edits one cell at a time, like a spreadsheet, in flat and tree mode alike. A column opts in with `meta.editor`, and the grid takes `onCommit`:

```tsx
const [startEditor, endEditor] = pairedEditors<Task, string | null, string | null>({
  start: dateEditor({ field: 'plannedStart', get: (t) => t.start, apply: (t, start) => ({ ...t, start }) }),
  end: dateEditor({ field: 'plannedEnd', get: (t) => t.end, apply: (t, end) => ({ ...t, end }) }),
  validate: ({ start, end }) =>
    start && end && end < start ? { end: 'End cannot be before Start.' } : undefined,
})

const columns: ColumnDef<Task>[] = [
  {
    accessorKey: 'name',
    header: 'Name',
    meta: {
      treeColumn: true,
      editor: textEditor({
        field: 'name',
        get: (t) => t.name,
        apply: (t, name) => ({ ...t, name }),
        validate: (name) => (name.trim() ? undefined : 'Name is required.'),
      }),
    },
  },
  { id: 'start', header: 'Start', meta: { editor: startEditor }, /* … */ },
  { id: 'end', header: 'End', meta: { editor: endEditor }, /* … */ },
]

<WaydGrid
  columns={columns}
  data={tasks}
  onCommit={(id, patch) => patchTask({ id, patch }).unwrap()}
  fieldToColumn={{ assigneeIds: 'assignees' }}
/>
```

An editor (`CellEditor`) says how one field moves between the row, the control and the request:

| Member | Purpose |
| --- | --- |
| `field` | The patch key, and what server errors call the field. A function when it differs by row — a milestone's Start column writes `plannedDate` |
| `get` | The field's value on a row, in the form the request sends (`'2026-03-01'`, an id, an id list) |
| `apply` | A copy of the row with a value in place. The grid shows a saving or failed value through it — in the cell and in anything drawn from the row, such as a Gantt bar — so `get(apply(row, v))` must give back `v` |
| `format` / `parse` | Request value → control value and back (a date string ↔ a Dayjs). Identity by default |
| `fromInput` | The control value when a typed character opened the cell, so typing replaces the value |
| `validate` | A message when the value cannot be sent; the cell keeps the value and is marked |
| `editable` | `(row, { isDraft })` — which rows' cells edit (a stage row, a milestone's End, a draft-only Type). A draft's row carries the values put on it, so a staged Type can turn another cell off |
| `requiredToCreate` | A draft is not created until this cell holds a value as well as its Name (a roadmap item's Start and End). A function `(row) => boolean` decides per draft from the values staged on it — a project plan draft needs its date only once its Type is Milestone |
| `equals` | Whether two values are the same; `Object.is` or element-wise for arrays by default, with `null`, `undefined` and `''` all empty |
| `render` | The control, given `value`, `onChange`, `commit`, `onPopupOpenChange`, `initialInput`, `status`, `aria-label` and the `row` |

`textEditor`, `numberEditor`, `selectEditor` (one choice, or `multiple`) and `dateEditor` build the common ones; pass them `field`, `get`, `apply` and any `validate` or `editable`. A select editor opens with its list showing and commits a single pick at once. A date editor keeps its calendar closed until it is clicked or opened with ↓, so a typed date (`YYYY-MM-DD`) commits on the first Enter or Tab like any other cell. A hand-built `render` passes `aria-label`, `aria-invalid` and `aria-describedby` on to its control, and calls `onPopupOpenChange` from its control's `onOpenChange`, or Escape cannot tell an open list from an edit to revert.

**Keys.** A click selects a cell, and in a grid that edits by cell the selected cell is outlined however it was chosen, as in a spreadsheet (a read-only grid outlines it for keyboard focus only). Enter, F2, a double-click, a click on the cell that already has focus, or typing a character opens the focused cell. In a text or number cell the typed character replaces the value; other editors just open. While it is open:

| Key | Does |
| --- | --- |
| Enter | Commit and move to the cell below. In an open list, picks the option instead |
| Tab / Shift+Tab | Commit and open the next / previous editable cell in on-screen order, wrapping across rows; past the last, leave the grid |
| Escape | Close an open list or calendar; otherwise revert the cell and return to it |
| Escape on an unsaved or failed cell | Discard its value — both cells' values, for a pair |

After Escape, or a pick from a list, focus goes back to the cell; Enter moves it down and Tab on to the next editor. Discarding an empty draft hands focus to the row that takes its place. A pointerdown anywhere outside the cell and its popups commits it — another cell, the empty body, a header, the toolbar, the chart pane — and so does focus leaving it. Popups count as inside because the grid renders the editor under a `ConfigProvider` whose `getPopupContainer` is an element it owns for that cell, never by antd class names. The grid's default help panel (`WaydGridKeyboardHelp`) is generated from the same keymap (`GRID_KEYMAP`), so a grid's help cannot drift from its keys; pass `children` to it for a grid's own notes.

**The footer and its key hints.** A grid that edits by cell has a footer: one line under its frame, kept in reserve so nothing moves when it fills. While a cell is selected or edited it shows the keys for what the user is doing — the cell's keys (Enter to edit only on a cell that edits, and only the row keys the grid supports), or the open editor's, by its `hintMode` (`text`, `select`, `multiselect`, `date`; the built-in factories set it, a custom editor reads as `text`). The hints come from `gridHintsFor`, kept beside `GRID_KEYMAP` so the two change together, and are hidden from assistive technology: the help panel and each control's own name cover them. The body renders them into the footer through a portal, since it knows the selection. Other footer content (a row count, an unsaved count) belongs in the same line.

**The commit.**

- **One field, sent once.** `onCommit(rowId, patch)` receives only the changed field. An unchanged value sends nothing, and nothing is ever read from the mounted DOM, so a hidden column or a row scrolled out of the virtual window cannot be read as cleared.
- **One at a time per row.** A second commit for the row waits for the first.
- **Optimistic.** The cell shows the new value, marked saving, at once; after success it keeps that value until the data next changes, so the old value never flashes back during the refetch.
- **Failure keeps the value.** Reject from `onCommit` — `.unwrap()` does, with RTK Query's `{ status, data }`, and the errors are read from `data` — and the cell keeps the user's value, is marked failed and takes focus if the user is still in the grid and no other cell is open; the message shows in a tooltip while the cell has focus, and a polite live region reads it out. A failure on a cell that is not on screen is toasted instead (when the page has a `MessageProvider`). Enter reopens it on that value; Escape discards it.
- **Server errors land on cells.** A 422's keys are matched to editors by `field` (any casing), or through `fieldToColumn` for keys named otherwise. Each message is prefixed with the column's label, never the field key, and a response with no field errors marks the committed cells with its `detail`.
- **No toast on success.**

**Server data** never overwrites an open, held or failed cell; every other cell follows the server. A refetch while the user types leaves the editor alone.

**Linked fields.** `pairedEditors({ start, end, validate })` links two editors. Moving between them (Tab from Start to End) holds the first value, marked unsaved; when focus leaves the pair, `validate` checks both values together and the changed ones go in one patch. A failed check marks the cells and sends nothing. A row with only one editable member (a milestone) commits that one alone, still through `validate`.

**Drafts.** With `createDraftNode` and `onCreate`, the `GridColumnContext`'s `addDraftAtRoot` / `addDraftAsChild` add a draft row and open its tree column. Values put on the draft's other cells are held locally — never sent through `onCommit`, a pair's included; once the tree column (its Name) and every editable `requiredToCreate` cell hold a value, the next commit on the draft runs `onCreate(parentId, values)` once with all of them, after each pair's `validate`; it should resolve with the new row's id. Until then a named draft marks the required cells it lacks ("Start: Required to create the item."), and Enter on its Name opens the first of them instead of moving down. Values the user changes while the create is in flight (an editor still open on the draft included) are then sent to that id through `onCommit`, and focus follows the new row. The draft stays on screen, showing its values but no longer editable, until the data has the new row, and the two swap in one render — so the row never disappears while the refetch runs and never shows twice; two data changes without the row drop the draft anyway. If the create fails, changing any of its cells retries it. Escape on a draft that holds nothing discards it. Tree rows must nest under `children`, as draft rows already require. A draft added below a row (Insert, see [Row-action keys](#row-action-keys)) sits directly under it, and `onCreate` gets a third argument, `{ order }`, its 1-based place among its siblings; one added last gets no third argument.

**Values set outside a cell.** `WaydGridHandle.commitCells(rowId, { [columnId]: value })` commits values that did not come from an editor — a dragged Gantt bar — through the same path: each editor's and pair's `validate` runs (the pair with the cell's held or the row's own value for any member not given), the cells show the values marked saving, and the commit waits behind the row's other commits. Unlike a cell's value, one that fails its check or the save is dropped, so the row — and anything drawn from it, such as its bar — goes back to what it was; the reason is toasted (when the page has a `MessageProvider`, else read out by the live region). No cell holds the value, so there is nowhere else to show it. A value the row already has is left out of the patch and drops whatever the cell held unsent. Columns the row cannot edit are ignored, and an editor open elsewhere is left alone. Values are in model form (what `get` returns), keyed by column id, so a milestone's date goes to its Start column and the editor's `field` decides the patch key. The project plan's `commitBarDates` is the reference.

**State on the cell.** A cell with an edit in flight carries `data-edit-state` (`unsaved`, `saving` or `error`) and a mark of its own shape — an underline for unsaved, a left bar for saving, a left bar on a tinted cell for failed — plus `aria-busy` while saving and `aria-invalid` when failed. Its state ("Unsaved.", "Saving.") or error is its accessible description, read from an element outside the table so it is not also part of the cell's name. While a value is unsaved, saving or failed, leaving the page asks first (`beforeunload`); a server error mark on a cell the user did not change does not.

**Rendering.** The row with an open editor stays mounted while scrolled away or while focus is in its popup, and the open cell drops its vertical padding (the editor's controls are 22px) so the row keeps its height. In tree mode the tree column's editor sits past the row's indent and expander slot (`--wayd-grid-tree-depth`), where the name is drawn, so a nested row's input does not jump left. Rows get the edit state as props (`cellMarks`, `editColumnId`), never by reading it off the TanStack `row` inside a compiled component.

### Row-action keys

A tree grid that passes `rowActions` answers to row keys, in navigation mode only — in an open editor the keys are the control's (Ctrl+Delete deletes a word). A grid without `rowActions` takes none of them, so a consumer opts in once its `onCreate` and `onNodeMove` keep the contract below. Indent and outdent are Microsoft Project's keys; Cmd stands in for Ctrl on a Mac, and Cmd+Backspace (a Mac's Delete key) deletes:

| Key | Does | Available when |
| --- | --- | --- |
| Insert / Ctrl+Enter | Adds a draft directly below the row, under the same parent, and opens its Name | Cell editing with drafts (`onCommit`, `onCreate`, `createDraftNode`), and `rowActions.canInsertUnder(parent)` allows it (`null` is the root) |
| Alt+Shift+→ | Indents the row as the last child of the sibling above it | Cell editing, `enableDragAndDrop` and `onNodeMove`, while not loading |
| Alt+Shift+← | Outdents the row to just after its parent | As above |
| Ctrl+Delete | `rowActions.onDelete(row)`; ask before deleting. Return `false` for a row that cannot be deleted | `rowActions.onDelete` |
| Ctrl+Shift+Enter | `rowActions.onOpen(row)`, the row's details; `false` as for delete | `rowActions.onOpen` |

- **Order.** Moves and inserts use the data order, so both are refused while the grid is searched, filtered or sorted, as dragging is. `onCreate` gets the new row's `{ order }` and must create it there in one request — created last and then moved, the row would show twice while the second request runs. The project task create endpoint takes an optional `order` for this.
- **Moves.** A move goes through `moveValidator` (or `defaultMoveValidator`) before `onNodeMove(id, parentId, order)`, and a second move waits for the first to land. A rejection — the validator's, or `onNodeMove` rejecting — reaches `onMoveRejected`, so `onNodeMove` should reject rather than report a failure itself. A row indented under a collapsed one expands it, and focus follows the moved row once the data shows it.
- **Saying why.** A matched key never falls through to navigation. A key the grid takes but cannot act on (no row above to indent under, a parent `canInsertUnder` refuses, a draft still open, a row `onDelete` declines) says why in the grid's polite live region, and a move that succeeds says "Indented." or "Outdented.". A rejected move is told through `onMoveRejected` instead when the grid has one, since its toast is already an alert. The messages are for screen readers; a sighted user sees only the toasts. Draft rows take none of these keys.
- **Help.** The default help panel lists the Rows section with only the keys the grid supports; pass `helpNotes` to add the grid's own notes after the keys rather than replacing the panel with `helpContent`.
- **Focus after a delete.** `WaydGridHandle.focusRow(rowId, columnId)` puts focus on a row once the data has it — the row taking a deleted row's place after the refetch, or the row itself when its delete is cancelled.

The project plan is the reference consumer.

### Chart pane

`rightPane` (`WaydGridRightPane`) attaches a chart to the right of the grid that shares the grid's row geometry — one virtualizer and one vertical scroller, so a bar cannot drift from its row. The consumer supplies the pane `header` (a date axis, typically) and `renderRow`, which receives each row with its resolved `top` and `height` and returns that row's bars; `renderBackground` draws chart-wide layers such as gridlines. The grid knows nothing about dates. The roadmap items grid and the project plan table use it for their Gantt views.

## Row grouping

Providing `grouping` (column ids, outermost first) groups a **flat** grid: each distinct value of the column becomes a collapsible heading row spanning the grid, with the matching rows underneath. The grouped column leaves the row cells, since its value is now the heading. Filters and quick search apply to the rows before they are grouped, so a group with no match disappears; sorting applies within each group, and the groups themselves come out in the grouped column's order (give that column a `sortFn` when its values have an order of their own, such as a health scale). The Projects Dashboard is the reference consumer.

```tsx
<WaydGrid<ProjectListDto>
  data={projects}
  columns={columns}
  grouping={['portfolio']}
  renderGroupHeader={({ value, leafRows }) => `${value} · ${leafRows.length} projects`}
  initialGroupsExpanded
/>
```

- The default heading is the value and a row count; `renderGroupHeader` replaces it and receives the group's `leafRows` so the heading can say what they add up to.
- Headings are not records: row activation, the displayed-rows surfaces (`onDisplayedRowsChange`, `getDisplayedRows`) and the CSV export see only the rows. The grouped column leads the CSV, so each exported row keeps the value its heading carried on screen. Flat row reorder turns off while grouped, since the displayed order is no longer the data order.
- Regrouping resets every group to `initialGroupsExpanded`, so a grid regrouped by another column opens fully rather than inheriting collapsed ids from the previous grouping.
- Grouping is for flat grids; a tree (`getSubRows`) already has its hierarchy and ignores it.

## CSV export

The toolbar export button downloads the **currently visible** columns (respecting hide/pinning/order) and the **filtered + sorted** rows, in display order. Grouped headers export as band rows above the leaf headers. Control it per column with `meta.enableExport`, `meta.exportHeader`, and `meta.exportFormatter`; name the file with the `csvFileName` prop (default `grid-export`), to which the download adds a timestamp.

## Conventions

- **Case-insensitive sorting** — never plain-`.sort()` user-facing lists; use `caseInsensitiveCompare` from the barrel. For a column's `sortFn`, the barrel also carries `dateSortBy(getDate)`, `workItemKeySort` (`WEB-9` before `WEB-10`), and `workStatusCategorySort` (workflow order); `sortEmptyLast` is every column's default.
- **Context-redundant columns** (e.g. a Project column on a single project's page) — omit them from the defs conditionally rather than `meta.unavailable`, so they stay out of the chooser and persisted layouts. Don't def-exclude a column named in `initialSorting`.
- **Theme tokens only** — the grid styles from Ant Design tokens; don't hardcode colors in cells.
