# MCP Server

Wayd provides an [MCP (Model Context Protocol)](https://modelcontextprotocol.io) server that lets AI assistants like Claude interact directly with your Wayd instance. The MCP server exposes Wayd's API as structured tools that AI agents can call to read and manage your delivery data.

**Package:** [`@wayd/mcp`](https://www.npmjs.com/package/@wayd/mcp)

## What Can It Do?

The MCP server exposes 150+ tools across Wayd's core modules:

| Module | Capabilities |
|--------|-------------|
| **[PPM](../user-guide/ppm/index.mdx)** | List/view portfolios, programs, projects, stages, tasks. Create and update portfolios, programs, projects, and tasks. Change status (approve, activate, complete, cancel, close, archive). View project plan tree, summary metrics, and status history. Get critical path. Manage task dependencies. Review and log project health checks. Review project scores and portfolio ranking. |
| **[Strategic Initiatives](../user-guide/ppm/strategic-initiatives.mdx)** | List/view initiatives, their statuses, and the projects delivering them. Review KPIs, checkpoints, and the checkpoint plan with health and trend. Record and remove KPI measurements. Change initiative status. |
| **[Planning](../user-guide/planning/index.mdx)** | List/view planning intervals, iterations, objectives, risks. Get PI predictability and health reports. Review and log objective health checks. View calendars. |
| **[Roadmaps](../user-guide/planning/roadmaps.mdx)** | List/view roadmaps and their items (activities, milestones, timeboxes). |
| **[Story Maps](../user-guide/planning/story-maps.mdx)** | List story maps and read a full map — goals, steps, tasks (with checklists, personas, and work item links), swim lanes, and personas. Create and manage maps: build out goals/steps/tasks, reorder and move cards, manage swim lanes, personas, checklists, and work item links. |
| **[Organizations](../user-guide/organizations/index.mdx)** | List/view teams and users. |

## Prerequisites

1. A running Wayd instance with API access
2. A **[Personal Access Token (PAT)](./your-profile.mdx#personal-access-tokens)** — create one from your profile page
3. **Node.js 22+** installed on your machine

## Setup

### Claude Desktop

Add the following to your Claude Desktop configuration file:

- **macOS:** `~/Library/Application Support/Claude/claude_desktop_config.json`
- **Windows:** `%APPDATA%\Claude\claude_desktop_config.json`

```json
{
  "mcpServers": {
    "wayd": {
      "command": "npx",
      "args": ["-y", "@wayd/mcp"],
      "env": {
        "WAYD_API_BASE_URL": "https://your-wayd-instance.com",
        "WAYD_API_KEY": "your-personal-access-token"
      }
    }
  }
}
```

### Claude Code

Add a `.mcp.json` file to your project root:

```json
{
  "mcpServers": {
    "wayd": {
      "command": "npx",
      "args": ["-y", "@wayd/mcp"],
      "env": {
        "WAYD_API_BASE_URL": "https://your-wayd-instance.com",
        "WAYD_API_KEY": "your-personal-access-token"
      }
    }
  }
}
```

Or set environment variables in your shell and omit the `env` block:

```bash
export WAYD_API_BASE_URL="https://your-wayd-instance.com"
export WAYD_API_KEY="your-personal-access-token"
```

### VS Code / Cursor

Add to your `.vscode/mcp.json` or workspace settings:

```json
{
  "inputs": [
    {
      "id": "waydBaseUrl",
      "description": "Wayd API base URL",
      "type": "promptString"
    },
    {
      "id": "waydApiKey",
      "description": "Wayd API key (Personal Access Token)",
      "type": "promptString",
      "password": true
    }
  ],
  "servers": {
    "wayd": {
      "type": "stdio",
      "command": "npx",
      "args": [
        "-y", "@wayd/mcp",
        "--base-url", "${input:waydBaseUrl}",
        "--api-key", "${input:waydApiKey}"
      ]
    }
  }
}
```

## Configuration

The MCP server accepts configuration via environment variables or CLI arguments:

| Environment Variable | CLI Argument | Description |
|---------------------|-------------|-------------|
| `WAYD_API_BASE_URL` | `--base-url` | The base URL of your Wayd API instance |
| `WAYD_API_KEY` | `--api-key` | Your [Personal Access Token](./your-profile.mdx#personal-access-tokens) |

CLI arguments take precedence over environment variables.

## Agent Skills

For Claude Code users, eight pre-built skills provide guided workflows:

- **`/wayd-ppm`** — Portfolio, program, project, and strategic initiative operations, including scoring, health checks, status changes, and tasks
- **`/wayd-pi`** — Planning intervals, iterations, objectives, and risks
- **`/wayd-products`** — The product catalog, plus the product types and tag axes it is built from
- **`/wayd-delivery`** — Releases, versions, release packages, deployments, environments, and delivery metrics
- **`/wayd-roadmaps`** — Roadmap exploration with activities and milestones
- **`/wayd-story-maps`** — Story map analysis and management with goals, steps, tasks, swim lanes, and personas
- **`/wayd-teams`** — Team lookup and resolving team names to IDs
- **`/wayd-users`** — User lookup and resolving names to UUIDs for assignees and project roles

Install the skills:

```bash
npx skills add destacey/wayd
```

The catalog is one typed tree of what your organization owns — products, platforms, services, and tools. A product's **type** carries the flag that decides whether versions can be cut against it, which is why a product line usually holds no versions of its own.

Three behaviours worth knowing. Tagging an axis that only allows one value **silently replaces** the existing tag rather than refusing. Deleting a product is a **hard delete**, unlike delivery, where records are withdrawn and kept. And seeded system types and axes **cannot be edited or deleted, but can be deactivated** — so an organization can hide a type it doesn't use. Individual tags inside a seeded axis are the exception: they can't be deactivated either, so retire the whole axis instead.

### Product Delivery

Where the catalog records what exists, delivery records what shipped. The word "release" means three different things in most organizations, and Wayd keeps them apart: a **release** is what was announced to customers (`Wayd 2026.07`), a **version** is one artifact that was built (`Wayd API 4.12.0`), a **package** is what moved through environments together (`WAYD-2026.07`), and a **deployment** is one of those reaching one environment.

| Tool | Description |
|------|-------------|
| `Releases_GetReleases` / `Releases_GetRelease` | List releases, or get one |
| `Releases_GetStatusHistory` | A release's status change history |
| `Releases_Plan` / `Releases_Update` | Plan a release, or update its details |
| `Releases_SetContents` | Set what the release announces — its versions and packages together |
| `Releases_MarkReleased` | Announce a release |
| `Releases_Withdraw` / `Releases_Revert` | Withdraw a release, or revert it to an earlier state |
| `Releases_CorrectDates` / `Releases_MoveTargetDate` | Correct recorded dates, or move the target |
| `Versions_GetVersions` / `Versions_GetVersion` | List versions, or get one |
| `Versions_GetStatusHistory` | A version's status change history |
| `Versions_Plan` / `Versions_Update` | Plan a version, or update its details |
| `Versions_Cut` | Cut the version — the artifact now exists |
| `Versions_MarkReleased` | Mark a version released |
| `Versions_Withdraw` / `Versions_Revert` | Withdraw a version, or revert it |
| `Versions_CorrectDates` / `Versions_MoveTargetDate` | Correct recorded dates, or move the target |
| `ReleasePackages_GetReleasePackages` / `ReleasePackages_GetReleasePackage` | List packages, or get one |
| `ReleasePackages_GetStatusHistory` | A package's status change history |
| `ReleasePackages_Assemble` | Assemble a package |
| `ReleasePackages_SetManifest` | Replace what the package contains |
| `ReleasePackages_MarkReleased` / `ReleasePackages_Withdraw` | Mark a package released, or withdraw it |
| `Deployments_GetDeployments` / `Deployments_GetDeployment` | List deployments, or get one |
| `Deployments_GetStatusHistory` | A deployment's status change history |
| `Deployments_Start` | Record a deployment starting — of a version or a package, never both |
| `Deployments_Succeed` / `Deployments_Fail` / `Deployments_RollBack` | Record how a deployment ended |
| `DeploymentEnvironments_GetDeploymentEnvironments` | List environments, by active state or category |
| `DeploymentEnvironments_Create` / `DeploymentEnvironments_Update` | Define or edit an environment |
| `DeploymentEnvironments_SetActive` | Retire an environment, or reinstate it |
| `DeliveryMetrics_GetDeliveryMetrics` | Deployment frequency and change failure rate over a window |

**Contents and manifests replace as a set.** `Releases_SetContents` and `ReleasePackages_SetManifest` overwrite what was there, so send the full list including anything that should stay.

Environments are **retired, never deleted**, because historical deployments still point at them. Every production-scoped measure counts on an environment's **category**, not its name — pipeline names vary too much (`prod`, `prd`, `live`) to reason about. Reclassifying an environment changes where future deployments count and leaves past ones alone.

`DeliveryMetrics_GetDeliveryMetrics` returns an `unavailable` list naming what it couldn't compute and why; read it rather than treating a missing measure as zero. Change failure rate is a **proxy** — a pipeline run that failed before production is a failure that was *prevented*, while a real change failure succeeded and then broke something, which the pipeline can't know.

## Changes That Ask First

Most tools only read data. The ones that change something a colleague relies on — changing a record's status, updating a portfolio, program, or project, or deleting anything — are flagged so your AI assistant asks for confirmation before running them.

Whether you actually see a prompt depends on the assistant you're using: the flag is a signal, and clients decide how to honour it. Your permissions are always enforced by Wayd itself regardless of what any client does.

Two behaviours worth knowing before you approve one:

- **Updates replace the whole record.** Anything not included in an update is cleared rather than left alone. This matters most for people: sponsors, owners, managers, and members are replaced as a set, so an update must carry the full team to keep it. Your assistant is instructed to read a record before updating it and pass back everything that should stay the same.
- **Activating a portfolio sets its start date to today, and closing it sets its end date to today.** Neither can be backdated, so avoid using them to tidy up a portfolio that really started or ended earlier.

Deleting a portfolio, program, project, or strategic initiative isn't available through the MCP server at all.

## Security

The MCP server authenticates using your [Personal Access Token](./your-profile.mdx#personal-access-tokens). The token inherits your permissions — the MCP server can only access what you can access.

- Store your API key securely — don't commit it to version control
- Use environment variables rather than hardcoding in config files
- Revoke tokens from your [profile page](./your-profile.mdx#personal-access-tokens) if compromised

Changing a portfolio, program, or project additionally requires **delivery leadership** — being an Owner or Manager on the record or on one above it. Having permission to view or edit is not enough on its own, and sponsors and project members are excluded. If a change is refused even though your token has the right permission, this is usually why. See [Permissions](../user-guide/settings/permissions.mdx) for details.
