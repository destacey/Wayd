# API Reference

The Wayd API is a RESTful ASP.NET Core Web API.

## Base URL

- **Local Development**: `https://localhost:5001` (or dynamic port via Aspire)
- **Swagger UI**: `https://localhost:5001/swagger`

## Authentication

All API requests require a **Wayd JWT** in the `Authorization: Bearer` header, regardless of which login provider the user authenticated with. The JWT carries the user's identity and permission claims and is minted by one of two login flows:

### Username / password

Authenticate with the local login endpoint:

```
POST /api/auth/login
{
  "userName": "your-username",
  "password": "your-password"
}
```

The response is the same shape for every login flow:

```
{
  "token": "<wayd-jwt>",
  "refreshToken": "<wayd-refresh-token>",
  "tokenExpiresAt": "2026-04-21T19:00:00Z",
  "mustChangePassword": false
}
```

Include the Wayd JWT in subsequent requests:

```
Authorization: Bearer {token}
```

### Microsoft Entra ID (token exchange)

For users authenticating via Microsoft Entra ID, the frontend obtains an access token from the OIDC provider (via `oidc-client-ts`) for the API scope and exchanges it for a Wayd JWT:

```
POST /api/auth/exchange
{
  "provider": "MicrosoftEntraId",
  "subjectToken": "<entra-access-token-from-oidc-client>"
}
```

The response shape is identical to `/login`. The provider token is only used during the exchange — all subsequent API calls use the Wayd JWT.

Deployments can disable Entra exchange (e.g., local-only customers); the endpoint returns HTTP 503 when disabled. Use `GET /api/auth/providers` (anonymous) to discover which providers are enabled.

### Refreshing tokens

When the Wayd JWT expires, exchange the refresh token for a new JWT:

```
POST /api/auth/refresh-token
{
  "token": "<expired-wayd-jwt>",
  "refreshToken": "<wayd-refresh-token>"
}
```

Same response shape. Refresh works uniformly for both login providers — the refresh flow doesn't need to know how the user originally authenticated.

Refresh tokens **rotate**: each refresh returns a new one and invalidates the one you presented. Store the new value and discard the old.

Presenting a refresh token that was already rotated away is treated as **reuse** — evidence that two parties hold tokens from the same chain — and revokes that session. Other sessions are unaffected. A client that keeps a single in-flight refresh will never trigger this; one that races several concurrent refreshes can.

### Sessions

Each sign-in creates a session. Signing in on a second device does not invalidate the first.

Signing out ends the calling device's session:

```
POST /api/auth/logout
{
  "refreshToken": "<wayd-refresh-token>"
}
```

Returns `204`. The refresh token identifies **which** session to end — without it, or with one that matches no live session, nothing is revoked.

To end every session:

```
POST /api/auth/logout-all
```

To list live sessions:

```
POST /api/auth/sessions
{
  "refreshToken": "<wayd-refresh-token>"
}
```

Returns device label, IP address, timestamps, and `isCurrent` marking the caller's own session. The refresh token is optional and only used to set `isCurrent`; the response never contains a token or hash. This is a `POST` rather than a `GET` so the token stays out of URLs, access logs, and browser history.

To end one session by id:

```
DELETE /api/auth/sessions/{sessionId}
```

Returns `204`, or `404` when the id is not one of the caller's live sessions.

All four endpoints require authentication and act only on the calling user — no user id is read from the request.

:::note
Revoking a session stops it refreshing, but that device's existing JWT stays valid until it expires (`TokenExpirationInMinutes`, 60 by default). Revocation is not instant.

Personal access tokens are **not** sessions and are unaffected by sign-out. Revoke them separately.
:::

### Personal Access Tokens (PATs)

**Personal Access Tokens** provide a way to authenticate API requests without interactive login. They are ideal for scripts, CI/CD pipelines, and integrations.

To use a PAT, include it in the `x-api-key` header:
```
x-api-key: your-personal-access-token
```

**Managing PATs:**
- Navigate to your [Profile](../getting-started/your-profile.mdx#personal-access-tokens) page
- Click **Personal Access Tokens**
- **Create** a new token with a name and optional expiration date
- Copy the token immediately — it cannot be retrieved after creation
- **Revoke** tokens that are no longer needed

PATs inherit the permissions of the user who created them. See [Your Profile](../getting-started/your-profile.mdx#personal-access-tokens) for details on creating and managing tokens.

## PPM Ranking Endpoints

Portfolio project ranking is exposed under `/api/ppm/portfolios`:

- `PUT /api/ppm/portfolios/{id}/project-ranks` — Reposition an ordered batch of projects within a portfolio's ranking.
- `PUT /api/ppm/portfolios/{id}/project-ranks/rebalance` — Re-space a portfolio's ranks to clean whole-number gaps.
- `GET /api/ppm/portfolios/{id}/ranking-scoreboard` — Get the current scoring-model breakdown used by the portfolio Ranking tab.

## Background Job Endpoints

Background jobs are exposed under `/api/admin/background-jobs`. See [Background Jobs](../user-guide/settings/index.mdx#background-jobs) for what the corresponding UI does.

Reading — all require `Permissions.BackgroundJobs.View`:

- `GET /api/admin/background-jobs/jobs?state=&pageNumber=&pageSize=` — A page of jobs in one lifecycle state. `pageNumber` is 0-based; `pageSize` is clamped to 1–500.
- `GET /api/admin/background-jobs/jobs/{jobId}` — Full detail for one job: arguments, state history, and the exception with its stack trace when the job failed.
- `GET /api/admin/background-jobs/statistics` — Counts split into current and all-time groups.
- `GET /api/admin/background-jobs/servers` — Worker processes and their heartbeats.
- `GET /api/admin/background-jobs/recurring` — Registered recurring schedules.
- `GET /api/admin/background-jobs/job-types` — The job types available to run.
- `GET /api/admin/background-jobs/running` — Currently processing jobs.

Acting — `Run` triggers work, `Delete` removes it:

- `POST /api/admin/background-jobs/run?jobTypeId=` — Queue a job to run now. Requires `Permissions.BackgroundJobs.Run`.
- `POST /api/admin/background-jobs` — Register a recurring job. Requires `Permissions.BackgroundJobs.Run`. Job types that cannot be scheduled are rejected with a 400.
- `POST /api/admin/background-jobs/jobs/{jobId}/requeue` — Queue a job for another attempt. Requires `Permissions.BackgroundJobs.Run`.
- `DELETE /api/admin/background-jobs/jobs/{jobId}` — Delete a job. Requires `Permissions.BackgroundJobs.Delete`.
- `DELETE /api/admin/background-jobs/recurring/{recurringJobId}` — Remove a recurring schedule. Requires `Permissions.BackgroundJobs.Delete`.
