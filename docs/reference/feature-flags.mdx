# Feature Flags

Wayd uses Microsoft.FeatureManagement to control feature visibility. Feature flags are defined in code, stored in the database, and managed through the Settings UI.

## How It Works

1. Flags are **defined in code** (`FeatureFlags.cs`). The definition is the only source of a flag's display name, description and module; none of them can be edited in the app.
2. On startup, the **seeder** makes the stored flags match the definitions:
   - creates a missing flag, **disabled** unless the definition sets `DefaultEnabled: true`;
   - reapplies each definition's display name, description and module to its stored flag;
   - **archives** a stored flag the code no longer defines, which also turns it off, and restores it if the definition comes back.

   It never changes whether a flag is enabled, so admin choices survive deploys.
3. Admins turn flags **on and off** on **Settings → System → Feature Flags**, which groups them by module
4. A **database-backed provider** serves flag state with caching

## Modules

Every flag belongs to a `FeatureFlagModule` (Platform, Planning, Organization, Product Management, Demand Management). The enum's `[Display]` attributes give each module its name, description and order on the page. Modules are stored by name: reorder them freely, but never rename a value.

A flag that turns a whole module on or off sets `IsModuleSwitch: true` — at most one per module (`FeatureFlagsTests` checks). The page shows it in the module's header and disables the module's other switches while it is off. That dependency is presentation only: a feature inside the module still has to check the module's flag itself, as Incident Management checks Product Management.

## Adding a New Feature Flag

### 1. Define the Flag

In `Wayd.Common.Domain/FeatureManagement/FeatureFlags.cs`:

```csharp
public static class FeatureFlags
{
    public static readonly FeatureFlagDefinition MyNewFeature =
        new(Names.MyNewFeature, "My New Feature", "What turning this on makes available.", FeatureFlagModule.Planning);

    // Seed a flag as ENABLED by default (e.g. rolling out a replacement UI):
    public static readonly FeatureFlagDefinition MyDefaultOnFeature =
        new(Names.MyDefaultOnFeature, "My Default-On Feature", "Enabled on first seed.", FeatureFlagModule.Platform, DefaultEnabled: true);

    public static class Names
    {
        public const string MyNewFeature = "my-new-feature";
        public const string MyDefaultOnFeature = "my-default-on-feature";
    }
}
```

The description is shown beneath the flag's name on the Feature Flags page, so write it for an administrator deciding whether to turn the flag on. Never rename a flag's `Name`: the seeder would archive the old flag and create a new, disabled one.

### 2. Gate the Backend

On a controller or action:
```csharp
[FeatureGate(FeatureFlags.Names.MyNewFeature)]
[HttpGet]
public async Task<ActionResult<MyDto>> Get() { ... }
```

Use the controller attribute for an endpoint that exists only with the flag on. For behaviour a flag changes inside an endpoint, inject `IFeatureFlags` (`Wayd.Common.Application.FeatureManagement`) into the handler — the application layers do not reference Microsoft.FeatureManagement:
```csharp
if (!await _featureFlags.IsEnabled(FeatureFlags.Names.MyNewFeature, cancellationToken))
    return Result.Failure("Feature is not enabled.");
```

### 3. Gate the Frontend

Page-level gate:
```typescript
export default requireFeatureFlag(MyPage, 'my-new-feature')
```

While the flag is off, the page answers 404.

Conditional rendering (the hook returns `{ isEnabled, isLoading }` and takes the
kebab-case flag name):
```typescript
const { isEnabled, isLoading } = useFeatureFlag('my-new-feature')
if (isLoading) return <Spin />
if (!isEnabled) return <LegacyView />
return <NewView />
```

### 4. Gate Menus

Pass flag state into menu builder functions to conditionally show navigation items.
