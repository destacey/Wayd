# Bulk Import

Wayd can load organization data in bulk from CSV files through a set of **import endpoints**. These are
useful for standing up an environment, onboarding a company's people and teams, or migrating from an HRIS or
another tool. Each import is a single `POST` of one CSV file (`multipart/form-data`, field name `file`), and
each is gated by a permission.

:::info[Screen or API]
Every import described here can be run from [Settings → System → Imports](../settings/imports.mdx#importing-a-file),
which lists each file's columns and hands over a template. Files can also be posted directly to the
endpoints below (for example with `curl`, a script, or the
[`wayd-data` data-generation tool](../../contributing/tools/data-generation.mdx), which generates these
exact CSVs and posts them for you). Exact request/response shapes are also in the API reference the API
serves at `/scalar`.

However it was submitted, the run is visible in **Settings → System → Imports**, where you can see what became of
each row and act on a run that did not finish. See [Imports](../settings/imports.mdx).
:::

## How imports work

A few rules apply to every import:

- **References are by natural key, not ID.** A CSV cannot carry Wayd's generated IDs, so rows reference each
  other by human-readable keys — an employee by their **employee number**, a team by its **code**, and a role
  by its **name**. A manager, a team parent, or a staffing assignment is expressed with those keys.
- **A successful post returns the run**, not the records it created. Every file is applied by a
  background worker, and the post waits a few seconds for it: a small file comes back finished
  (`200 OK`) with its counts, and a large one comes back still queued or running (`202 Accepted`) with a
  `Location` to follow. Either way the body is the same run, and it has its own page under
  [Settings → System → Imports](../settings/imports.mdx).
- **A file can be checked before it is imported.** Add `validateOnly=true` to the post, or choose
  **Check File** in [Settings → System → Imports](../settings/imports.mdx#checking-a-file-first), and every row goes
  through the import's own checks without anything being created: each comes back passed or rejected
  with its reason, and an all-or-nothing file reports every rejection rather than stopping at the first
  step that finds one. It is advice, not a promise — the data can change before you import — and a
  finished check can be imported for real from its page without posting the file again.
- **Files posted together can be grouped.** Every import endpoint takes an optional `submissionGroupId`
  query parameter — any GUID you choose — and records it on the run. Post a set of files under one value
  and [Settings → System → Imports](../settings/imports.mdx#what-you-see) shows them as one batch with summed
  counts, and each run's page links to the others; the
  [`wayd-data` seed](../../contributing/tools/data-generation.mdx) does this for each run. Leave it out
  to submit a file on its own. An empty GUID is rejected rather than treated as a group.
- **Teams, hierarchy and staffing are all-or-nothing; employees are applied row by row.** For the three
  team imports, any row that is rejected — an unknown employee number, team code, or role name, or a
  team name or code that is already taken — fails the **entire import**, and nothing is saved; the
  run shows each rejected row and why. The employee import instead rejects the offending row (a duplicate
  employee number or email, say) and keeps the rest, so a run can finish **partially succeeded**; the run
  shows which rows were rejected and why, and they can be retried once fixed. See [Limits](#limits).
- **`ImportId` is yours, and its cells may be blank.** Any value you like — a row number, a key from
  whatever system the file came out of — provided it is unique within the one file, compared
  case-insensitively. Row outcomes are reported against it, and leaving it blank uses the row's position
  instead. It is never written onto the records the import creates; the durable link runs the other way,
  as the id of the record each applied row reports creating.
- **Every column must be present, even the optional ones.** *Required* in the tables below means the cell
  needs a value; it does not mean the column can be left out. A missing header fails the file with
  a `400` that names it — `The CSV header has no column for … ('X')`. Headers match ignoring case and
  surrounding spaces. Include every column and leave unused cells blank.
- **Dates are ISO `yyyy-MM-dd`.** A date column takes a date, not a timestamp: a cell carrying a time
  is rejected rather than truncated.
- **A missing file returns 422**, not 400 — the file is a validation failure like any other.
- **Boolean and status columns are case-insensitive** and, where a column is optional, have a sensible
  default (noted per column below).
- **Multi-value columns are semicolon-separated.** A cell holding more than one value separates them with
  `;` — for example `ada@acme-legacy.example;a.lovelace@acme-legacy.example`. A comma would collide with the
  CSV field delimiter. Values are trimmed, and blanks are ignored.

Imports create records **through the normal domain rules**, exactly as if you had used the app. A useful side
effect: creating an organization record also replicates it into the PPM, Planning, and Work areas (for
example, creating a team makes it available to those areas), because the import goes through the same domain
path the app uses.

## Import order

Because records reference each other, imports must be run in dependency order:

```
Employees
  → Teams (and Teams of Teams)
  → Team hierarchy (team memberships)
  → Team staffing (team members)
  → KPIs (with their measurements and checkpoint plans)
```

- **Employees first** — teams are staffed with them, and employees reference their manager by employee
  number (a manager may appear anywhere in the same file or already exist).
- **Teams before hierarchy and staffing** — the [team hierarchy](#team-hierarchy-import) places teams under
  one another, and [staffing](#team-staffing-import) puts employees on teams, so both need the teams to exist.
- **Roles must already exist** — the staffing import resolves each row's role **by name** and fails if it
  does not exist or is inactive. Create the [team member roles](./index.mdx#team-members) you intend to use before importing
  staffing. (The [data-generation tool](../../contributing/tools/data-generation.mdx) creates any missing
  roles for you as a separate step before staffing.)

## Permissions

| Import | Permission |
|---|---|
| Employees | Import Employees |
| Teams | Import Teams and Teams of Teams |
| Team staffing · Team hierarchy | Manage Team Memberships |
| KPIs | Administer KPIs |

## Limits

| Import | Rows per file | Applied |
|---|---|---|
| Employees | 50,000 | Row by row |
| Teams | 10,000 | All-or-nothing |
| Team hierarchy | 10,000 | All-or-nothing |
| Team staffing | 10,000 | All-or-nothing |
| KPIs | 10,000 KPIs (measurements not counted) | KPI by KPI, each with its measurements |

A file over its cap is rejected before anything is queued, with a message naming the cap. Split a larger
export into several files and post them one at a time, waiting for each run; one `submissionGroupId`
across the parts keeps them findable as one import. The caps differ because an all-or-nothing file is one
database transaction, and 10,000 rows bounds it. A check of an employees file is one transaction too, so a
[preflight](../settings/imports.mdx#checking-a-file-first) takes at most 10,000 employees at a time.

The rules every file shares — request size, `ImportId` length, how rows are chunked, how long the post
waits, retries, stalls and retention — are in [Settings → System → Imports → Limits and rules](../settings/imports.mdx#limits-and-rules).

## Employees import

`POST /api/organization/employees/import`

Loads [employees](./index.mdx#team-members) and their management chain. Imported employees are
[owned by Wayd](./index.mdx#synced-and-wayd-owned-employees): no people sync changes or deactivates them, so
each needs an `AccessEndDate`, and a people sync takes one over only if it later sends the same person on the
key its connection matches on. A manager is referenced by employee
number and may appear **anywhere in the same file** or already exist — the import resolves managers after
creating everyone, so order within the file does not matter. An employee whose manager cannot be resolved is
still created (without a manager) rather than failing the batch, and the row carries a warning saying so.

A row is rejected, and the rest of the file still imported, when its employee number already belongs to an
employee or to an earlier row in the file, or when any of its addresses (`Email` or `AdditionalEmails`) is
already an employee's primary or additional address or is claimed by an earlier row. Employee numbers and
addresses are compared case-insensitively. A row that fails the column rules in the table below — a missing
name, a malformed address, a value too long — fails the whole file when it is posted, before anything is
queued.

:::note[Splitting a large export]
A file holds at most 50,000 employees, so a larger export goes in several files, posted **one at a time
and each waited for**. A manager resolves only if they are in the same file or already exist: a report
whose manager arrives in a *later* file is created without one, and the link is not made afterwards.
Order the files so managers precede their reports where you can, and post them under one
`submissionGroupId` so the runs read as one import.
:::

| Column | Required | Notes |
|---|---|---|
| `EmployeeNumber` | Yes | The employee's natural key, unique across the company. Max 64 chars, because a people sync that later takes the employee over uses it as the employee's id in the people system. |
| `FirstName` | Yes | Max 100 chars. |
| `MiddleName` | No | Max 100 chars. |
| `LastName` | Yes | Max 100 chars. |
| `Email` | Yes | A valid email address. Max 256 chars. |
| `AdditionalEmails` | No | Other **work** addresses this person is known by, semicolon-separated. Each must be a valid address, max 256 chars, and must not repeat the row's own `Email`. |
| `HireDate` | No | The date the employee was hired. Unlike the other date columns, this one also accepts a timestamp, read as UTC. |
| `JobTitle` | No | Max 256 chars. |
| `Department` | No | Max 256 chars. |
| `OfficeLocation` | No | Max 256 chars. |
| `ManagerNumber` | No | The manager's **employee number**. May reference someone elsewhere in the file. |
| `IsActive` | No | Whether the employee is current. Defaults to `true`. |
| `EmployeeType` | No | Free-form worker type (e.g. `Employee`, `Contractor`, `Intern`), mirroring an HRIS descriptor. Max 128 chars. |
| `AccessEndDate` | Yes | The last day the employee keeps access, as `YYYY-MM-DD`. Once it has passed, Wayd deactivates the employee and any user linked to it. For a former employee, the day they left. |

:::note[Former employees]
Set `IsActive` to `false` to record someone who has left. Inactive employees are created active and then
deactivated through the domain, so the record is consistent — but note that an inactive employee **cannot
hold a current team membership**, so leave them out of the [staffing import](#team-staffing-import).
:::

:::note[Additional emails]
`AdditionalEmails` records other addresses the same person is known by — typically an address they used
before a domain or tenant move. Wayd matches people against connected systems on email, so an Azure DevOps
work item still stamped with someone's previous address resolves to them once that address is listed here.

Record **work addresses only**. Home and personal addresses serve no purpose for matching and should never be
loaded into Wayd.

An imported employee is owned by Wayd, so a people sync leaves its addresses alone. If a people sync later
takes the employee over, it owns the addresses from then on: each sync replaces them with exactly what the
source reports, so an address added by import is removed unless the source reports it too.
:::

## Teams import

`POST /api/organization/teams/import`

Loads [teams and teams of teams](./index.mdx#teams) in one file. The `Type` column discriminates between the
two; both share the same shape. Teams are flat here — the parent/child structure is set separately by the
[team hierarchy import](#team-hierarchy-import).

| Column | Required | Notes |
|---|---|---|
| `Type` | Yes | `Team` or `TeamOfTeams` (case-insensitive). |
| `Name` | Yes | Max 128 chars. Unique across teams and teams of teams, compared case-insensitively. |
| `Code` | Yes | The team's natural key: 2–10 uppercase letters/numbers. Unique across teams and teams of teams. |
| `Description` | No | Max 1024 chars. |
| `ActiveDate` | Yes | The date the team became active. |
| `IsActive` | No | Whether the team is current. Defaults to `true`. |
| `InactiveDate` | Conditional | Required when `IsActive` is `false`; must be **after** `ActiveDate`. Must be empty when active. |
| `Links` | No | Links to add to the team: `Name\|URL` entries separated by semicolons. See [Links](#links-column). |

A file that repeats a name or a code fails when it is posted. A row whose name or code already belongs to a
team is rejected, which fails the whole import. Each team is created with the same default operating model
as one created in the app — Kanban and Count, in the [system time zone](../settings/index.mdx#general), with
the grace period and working days from the [scheduling settings](../settings/index.mdx#scheduling) — and each
team of teams with an operating model in the system time zone. A row with `IsActive` set to `false` is created
active and then deactivated on its `InactiveDate`.

## Team hierarchy import

`POST /api/organization/teams/team-memberships/import`

Places teams under one another to build the org hierarchy — a value-stream / ART / team shape, for example.
Each row puts a **child** (a team or a team of teams) under a **parent** (which must be a team of teams) for a
date range.

| Column | Required | Notes |
|---|---|---|
| `ChildCode` | Yes | The child team's code. May be a Team or a Team of Teams. |
| `ParentCode` | Yes | The parent's code. **Must be a Team of Teams.** Cannot equal `ChildCode`. |
| `Start` | Yes | When the membership begins. |
| `End` | No | When it ends. Must be on or after `Start`. Blank for a membership still in place. |

:::note[Multi-tier hierarchies]
Because a child may itself be a team of teams, chaining rows builds multiple tiers (for example a team under
an ART, and that ART under a value stream). The batch is all-or-nothing and rejects a code no team has, a
parent that is not a team of teams, a child or parent that is inactive, a membership that overlaps another
of the child's parent memberships (already in Wayd or earlier in the file), and a parent that is already
beneath the child, which would make a cycle.
:::

## Team staffing import

`POST /api/organization/teams/members/import`

Staffs teams — places employees on teams in named roles. Each row is one employee on one team in one role;
to give someone **multiple roles** on the same team, add multiple rows.

| Column | Required | Notes |
|---|---|---|
| `TeamCode` | Yes | The team or team of teams, by code. |
| `EmployeeNumber` | Yes | The employee, by number. Must be an **active** employee. |
| `RoleName` | Yes | A [team member role](./index.mdx#team-members), **by name** (case-insensitive). The role must already exist and be active. Max 128 chars. |

Rows add to whoever is already on the team: a person already a member gains the roles the file gives them.
A row giving someone a role they already hold on that team is rejected, which fails the whole import.

:::warning[Roles and active employees]
Two things fail the whole batch if not satisfied: the **role must already exist** (staffing does not create
roles — resolve them by name), and the **employee and team must both be active** (the domain does not allow
staffing an inactive person or team). Create any needed roles first, and omit former employees.
:::

## KPI import

`POST /api/kpis/import`

Loads [KPIs](./scorecards.mdx) onto existing teams, teams of teams, projects, programs, portfolios and strategic initiatives, each with its history and, optionally,
its checkpoint plan. Takes `file`, one row per KPI; `measurementsFile`, one row per measurement naming its KPI's
row; and, optionally, `checkpointsFile`, one row per checkpoint naming its KPI's row. Send the measurements file
with its header even when it has no rows. Needs the `kpis` feature flag.

KPI file:

| Column | Required | Notes |
|---|---|---|
| `ImportId` | Yes (column) | Your key for the row, unique within the file. The measurements file names it. A blank cell is known by its position. |
| `SubjectType` | Yes | `organization.team` for a team or a team of teams, `ppm.project`, `ppm.program`, `ppm.portfolio` or `ppm.strategic-initiative`. |
| `SubjectId` | Yes | The record the KPI goes on, **by id**. A KPI on a PPM record needs the [PPM import](../ppm/bulk-import.mdx) that created it to have run first. |
| `Name` | Yes | Max 128 chars. Unique on its team, ignoring case: a name the team already has, or one the file gives the same team twice, rejects the row. |
| `Description` | No | Max 1024 chars. |
| `CategoryId` | No | An active [KPI category](../settings/index.mdx#kpi-categories), by id. |
| `Prefix` · `Suffix` | No | Shown before and after a value, such as `$` or `days`. Max 16 chars each. |
| `ExpressedAs` | No | `Value` (default), `ChangeFromBaseline` or `ProgressToTarget`. |
| `Direction` | Yes | `Increase` or `Decrease`. |
| `BaselineValue` | Conditional | Where the KPI started. Required for a `RelativeChange` target, and must be short of the target in the KPI's direction. |
| `BaselineWindowStart` · `BaselineWindowEnd` | No | The dates the baseline was taken over. Give both or neither. |
| `TargetKind` | No | `Absolute` (default), a value to reach, or `RelativeChange`, a percentage change from the baseline. |
| `TargetValue` | Yes | The value to reach, or the percentage — `25` for 25%. |
| `AtRiskKind` · `AtRiskValue` | No | An at-risk threshold: `Absolute` with a value, or `ProgressToTarget` with a percentage of the way from baseline to target. Give both or neither. Must be short of the target. |
| `IsClosed` | No | `true` to import the KPI closed, as history only. |
| `WindowKind` | No | What span each measurement covers: `PerPeriod` (default), `Cumulative`, `Rolling` or `PointInTime`. See [measurement windows](./scorecards.mdx#measurement-windows). |
| `WindowAnchorDate` | Conditional | For `Cumulative` only, and required there: the first day every measurement covers. |
| `WindowRollingCount` · `WindowRollingUnit` | Conditional | For `Rolling` only, and required there: how many units each measurement covers, and `Days`. |
| `RollingAverageOf` | No | For `PerPeriod` only: read the KPI as the average of this many latest measurements, 2 to 12. |

Measurements file. Each row says when its value was taken **one way**, the way its KPI's `WindowKind` takes:

| Column | Required | Notes |
|---|---|---|
| `KpiImportId` | Yes | The `ImportId` of the KPI row the value belongs to. A value naming a KPI not in the file fails the whole submission. |
| `PeriodStart` · `PeriodEnd` | `PerPeriod` | The days the value describes. A KPI's periods cannot overlap. |
| `AsOf` | `Cumulative` · `Rolling` | The last day the value covers; Wayd works out its period from the KPI's window. One value per day. |
| `MeasuredAt` | `PointInTime` | The moment the value describes, as ISO 8601 **with its offset**: `2026-03-06T15:00:00-06:00` or `2026-03-06T21:00:00Z`. A time without an offset is refused, since it names no single moment. Several a day are allowed, one per moment. |
| `Value` | Yes | The raw value — never a percentage worked out from it. |
| `MeasuredOn` | No | The day it was taken; when blank, the last day it covers (for a moment, its day in the [system time zone](../settings/index.mdx#general)). |
| `SampleSize` | No | How many items an average or a rate was worked out from. |
| `Note` | No | Max 1024 chars. |

Checkpoints file, optional. Each row is one checkpoint of a KPI's [checkpoint plan](./scorecards.mdx#checkpoint-plans):

| Column | Required | Notes |
|---|---|---|
| `KpiImportId` | Yes | The `ImportId` of the KPI row the checkpoint belongs to. A checkpoint naming a KPI not in the file fails the whole submission. |
| `Date` | Yes | The day the planned value is due. One checkpoint per day on a KPI. |
| `Label` | Yes | A short name, such as `Q1` or `Sprint 12`. Max 32 chars. |
| `PlannedValue` | Yes | The value the KPI is expected to reach by then. |
| `AtRiskValue` | No | The value past which a measurement read against this checkpoint is at risk. Must be short of the planned value in the KPI's direction. |

Each KPI applies with its measurements and plan or not at all, and independently of the other rows: a goal the
KPI cannot hold, an unknown team or category, two values that clash, a value given a way its window does not
take, or a plan that cannot hold rejects that KPI alone, with the reason. New KPIs go after the team's existing ones, in file order. Imported measurements record no one as
having taken them.

Because a team's KPI names are unique, sending the same files again after fixing a failed row imports only
the rows that failed: every KPI that already imported is rejected as existing, not added a second time.

## Links column

The [teams import](#teams-import) takes an optional `Links` column, so a team arrives with its links
already on it.
The cell holds entries separated by semicolons, each a name and a web address joined by `|`:

```text
Charter|https://example.com/charter; Team wiki|https://example.com/wiki
```

- Only the first `|` in an entry separates the name from the address, so an address may contain one; a name
  cannot contain `|` or `;`.
- A `;` inside an address is written `%3B`, which is how URLs encode it anyway.
- Every address must be a full `http://` or `https://` address. An entry without a `|`, without a name, with a
  name over 128 characters or with any other address rejects its row, and the message names the entry.
  Because the teams import is all or nothing, that fails the whole file.
- A record may have the same address twice; the import creates what the file says.
- The import's own permission covers the links. Imports only create, so this adds links to the records the file
  creates, never to records already in Wayd.
