# Sprints & Metrics

## Sprints

A **Sprint** (also called an Iteration in some contexts) is a short time-boxed period — typically 2 weeks — during which a team implements and delivers [work items](./work-items.mdx#work-items).

Every sprint has:
- **Name** — Sprint identifier
- **Type** — Sprint or Iteration
- **State** — Future, Active, or Completed
- **Date Range** — The first and last planned days, as calendar dates. The sprint includes the whole of its last day
- **Team** — The owning [team](../organizations/index.mdx#teams) (optional)
- **Ownership** — Owned (by Wayd) or Managed (from external system like Azure DevOps)

Managed sprints may have **External Metadata** such as the Azure DevOps iteration path.

A sprint is **Future** until its first planned day, **Active** from its first planned day through the end of its last, and **Completed** after that. Days are counted in UTC, and the state is updated each time sprints sync.

Sprints are [mapped to PI iterations](../planning/planning-intervals.mdx#sprint-mapping) to connect team delivery cadence to the broader planning schedule.

### Starting, Completing and Reopening a Sprint

A sprint's synced dates are what was **planned**. Teams often start or finish on a different day — the planned Monday is a holiday, so they plan on the Friday before — so a team records when it **actually** started and completed the sprint in Wayd. Nothing is written back to Azure DevOps, and syncing never changes these dates.

| Action | What it records | When it is allowed |
|---|---|---|
| **Start** | The current moment, as the sprint's actual start | After the team's previous sprint started, up to the end of the sprint's last planned day. The team's first sprint can be started up to 3 days before its planned start. Only the team's next sprint can be started. |
| **Complete** | The current moment, as the sprint's actual end | Once the sprint has started — pressing Start is not required, its default start is enough — and before a later sprint has started |
| **Reopen** | Clears the actual end | While the team has not started a later sprint |

**A team has one open sprint at a time.** If the previous sprint is still open when you start the next one, Wayd asks you to confirm completing it. On confirm, the previous sprint is completed at the same moment the new one starts.

**Default dates.** A sprint the team does not start or complete still has actual dates for metrics:
- **Default start** — the end of the team's [commitment grace period](../organizations/index.mdx#operating-model) after the planned start (with the default of 1 day, the end of the first planned day)
- **Default end** — the end of the last planned day

Both are counted in the team's time zone, from the [operating model](../organizations/index.mdx#operating-model) in effect on the sprint's planned start. The sprint page labels each date **Actual** or **Default**, and shows the team's time zone when it differs from yours.

**Overlapping sprints in Azure DevOps.** Azure DevOps lets one team's iterations overlap, and Wayd keeps the source dates as they are. Where they overlap, a sprint's default end is cut to the next sprint's start, so the team's actual sprints never overlap. The sprint page and the team's Sprints section show a warning for overlapping sprints so they can be corrected at the source.

**Who can do it.** Members of the sprint's team, or of the team of teams it belongs to, who hold the `Permissions.Iterations.Update` permission. Holders of `Permissions.Iterations.Administer` can act on any team's sprints. Sprints whose Azure DevOps team is not mapped to a Wayd team cannot be started or completed. See [Permissions](../settings/permissions.mdx#sprint-lifecycle-team-membership).

**Moving a sprint to another team.** If Azure DevOps moves a sprint to a different team — for example after an area or iteration path changes — the sprint keeps the actual dates its team recorded. If it was open and the team it moved to already has an open sprint, the moved sprint is completed at the time of the sync, so the team still has one open sprint.

Every start, completion and reopening is recorded in the sprint's [Activity](../activity-log.mdx).

### Sprint Detail Page

The sprint detail page shows:
- **Actions** — Start, Complete and Reopen, when you may take them (see [above](#starting-completing-and-reopening-a-sprint))
- **Planned and actual dates** — the planned start and end, and the actual start and end, each labelled Actual or Default
- **Team** link and timeline progress bar
- **Sprint Metrics** (for Active/Completed sprints) — see [Sprint Metrics](#sprint-metrics) below
- **Backlog grid** — [Work items](./work-items.mdx#work-items) in the sprint with Rank, Key, Type, Title, Story Points, Status, Status Category, and Team
- **Activity** — the sprint's recorded history: what changed, who changed it, and when. See [Activity Log](../activity-log.mdx)
- **Links** section

A **Switch Sprint** dropdown lets you quickly navigate between other sprints on the same team.

### Sprints List Page

The sprints list (**Work Management > Sprints**) shows all sprints across all [teams](../organizations/index.mdx#teams) in a grid with Key, Name, Team, State, Start Date, and End Date, sorted by most recent start date. Started and Completed columns, showing the actual dates the team recorded, can be added from the column menu.

Teams also see their sprints in the [Sprints section](../organizations/index.mdx#sprints) of their detail page.

### Active Team Sprint Card

If you are a [team member](../organizations/index.mdx#team-members) of one or more teams, the **Home** page shows a **My Team Sprints** panel in the right column with an active sprint card for each of your teams (Teams only — Teams of Teams do not have sprints). The cards are sorted by team code.

Each card shows:
- **Team code** (links to the team page) and **sprint name** (links to the sprint page)
- **Sprint health indicator**
- **Timeline progress** — Days elapsed and percentage complete
- **Completion Rate**, **Velocity**, **In Progress**, and **Avg Cycle Time** metrics
- **Predictability** — If the sprint is mapped to a Planning Interval and the team has objectives, a predictability card appears per PI (links to the team's plan review page)

The panel is only visible if you have at least one active team sprint.

## Sprint Metrics

Sprint metrics provide quantitative insight into a sprint's progress and delivery. Metrics are available for both individual sprints and [PI iterations](../planning/planning-intervals.mdx#pi-iteration-detail-page) (which aggregate across all mapped sprints).

All metrics can be viewed using either **Story Points** or **Count** sizing, toggled via a selector.

### Metric Definitions

| Metric | Formula | Description |
|--------|---------|-------------|
| **Total** | Sum of all work items (or story points) in the sprint | Everything committed to the sprint |
| **Completed** | Items where status category is **Done** or **Removed** | Work that is finished or removed from scope |
| **In Progress** | Items where status category is **Active** | Work currently being performed |
| **Not Started** | Items where status category is **Proposed** | Work that hasn't begun yet |
| **Remaining** | Total − Completed | Work still to be done |
| **Completion Rate** | `(Completed / Total) × 100` | Percentage of sprint work completed. Target: 80% |
| **Velocity** | Completed count (story points or items) | How much work the team delivered. Percentage of total shown alongside. |
| **Avg Cycle Time** | `Sum(Done − Activated) / Count` for Done items with both timestamps | Average days from start to completion. Only includes items that moved through Active to Done. |
| **Missing Story Points** | Count of items with null or zero story points | Indicates estimation gaps. Highlighted red if any exist. |

### How "Completed" Is Defined

**Completed** includes both **Done** and **Removed** [status categories](./work-configuration.mdx#work-status-categories). Removed items are counted as completed because they represent work that has been resolved (even if by removal from scope) and is no longer in progress.

This means:
- `Remaining = Total − (Done + Removed)`
- `Completion Rate = (Done + Removed) / Total × 100`

### Cycle Time in Sprint Context

**Average Cycle Time** is only calculated from work items that:
1. Have a **Done** status category (not Removed)
2. Have both an **Activated Timestamp** and a **Done Timestamp**
3. The Done timestamp is after the Activated timestamp

```
Per item: Cycle Time = Done Timestamp − Activated Timestamp (in days)
Sprint average: Sum(all item cycle times) / Count(eligible Done items)
```

Items that were moved directly to Done without being Activated, or items that were Removed, are excluded from the cycle time calculation.

For a deeper analysis of cycle time patterns over longer periods, use the [Cycle Time Report](./cycle-time-report.mdx) on individual team or employee pages.

### PI Iteration Metric Aggregation

When viewing a [PI iteration](../planning/planning-intervals.mdx#pi-iteration-detail-page), metrics are aggregated from all mapped team sprints:
- **Counts and story points** are summed across all sprints (Total, Completed, In Progress, Not Started, Missing)
- **Average Cycle Time** is the average of each sprint's average cycle time (simple average, not weighted)
- **Team Count** and **Sprint Count** show how many teams and sprints are included
